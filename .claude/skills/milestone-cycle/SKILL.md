# 開発サイクル

オーケストレーター（メインのセッション）が、1つの作業単位を最初から最後まで運ぶための手順。
オーケストレーターは実装しない。仕様を書き、委任し、統合し、報告する。
**ゲートの記録と統合の可否は `scripts/cycle.py` が担う**（`docs/design/harness.md`）。条件を満たさない統合はスクリプトが拒むので、手で `git merge` しない。
コマンドは Windows、macOS、Linux で同じ。Windows では `python scripts/cycle.py …`、`python scripts/check.py` のように、先頭に `python` を付けて実行する（下の例の `scripts/cycle.py …` は、そのように読み替える）。

## 全体の流れ

| ゲート | やること | 担当 | 通過の条件 |
|---|---|---|---|
| G0 仕様 | `docs/plan/<ID>-<名前>.md` を書く | オーケストレーター | 目的、範囲、範囲外、受け入れ基準（測れる形）、担当が書かれている |
| G1 実装 | ブランチ（または作業ツリー）で実装 | 担当エージェント | 担当者が基準を実測し、`python scripts/check.py` が通る |
| G2 レビュー | 差分を読む | code-reviewer | 重大な指摘がゼロ |
| G3 独立検証 | 基準を別の立場で実測 | verifier | 全基準が合格、未確認なし |
| G4 UX確認 | 画面を動かして判定（画面を含む場合のみ） | ux-designer | 合格 |
| G5 統合 | `main` に取り込む | オーケストレーター | `python scripts/check.py` が通る、文書を更新 |
| G6 報告 | `docs/plan/po-board.md` を更新 | オーケストレーター | 下の形式で書かれている |

## 手順

### G0 仕様を書く

1. `docs/plan/roadmap.md` から次の作業単位を選ぶ。依存する作業が終わっているか確かめる。
2. 仕様ファイルを書く。先頭に見出し（`id`、`owner`、`needs_ux`）を付ける。受け入れ基準は「何を、どう測り、いくつなら合格か」まで書く。根拠の無い数字を置かない。
   見出しに書けるのは `id`、`owner`、`needs_ux`（`true` か `false` だけ）、`gates` の4つ。それ以外の行や値、`needs_ux` と `gates` の食い違いは `start` がエラーにする。ゲートを記録した後で見出しを変えると `start` も `merge` も拒む。変えるなら `scripts/cycle.py start <ID> --reset` で記録を消し、ゲートをやり直す。
   `needs_windows: true` を書くと、統合の条件に「そのツリーに対する、Windowsでの合格の記録」が加わる。OSの違いが出やすい作業（`scripts/`、ファイルの読み書き、文字コード、プロセスの起動、画面）に付ける。数値計算だけの作業には付けない（D-032）。
3. 画面を含む作業は、先に ux-designer に画面仕様を書かせ、それを仕様から参照する。
4. 範囲が1回の実装で収まらないなら、a / b に割る。

### G1 実装を委任する

1. 作業ツリーを作る: `scripts/cycle.py start <ID>`
2. 担当エージェントを動かす。ヘッドレスなら `scripts/cycle.py run <ID> implement`。セッション内で起動するなら、役割の定義ファイル、作業場所、仕様ファイル、報告の形式を渡し、終わったら `scripts/cycle.py record <ID> implement --verdict pass --by <名前>` で記録する。会話の文脈は伝わらないので、必要なことは仕様に書いておく。
   セッション内のエージェントは、返信を終えると止まる。完了を見届けてから返信する。
3. 互いに触るファイルが重ならない作業は並行で走らせてよい。同じファイルを触る作業は順番にする。
4. 報告を受けたら、差分と実測値を自分でも確かめ、`scripts/cycle.py check <ID>` を実行する。

### G2 / G3 / G4 確認を委任する

1. code-reviewer と verifier は並行で走らせてよい。どちらにも実装者の報告を鵜呑みにしないよう伝える。ヘッドレスなら `scripts/cycle.py run <ID> review` と `run <ID> verify`。セッション内なら、確認を始める前に `scripts/cycle.py snapshot <ID>` で対象のツリーIDを控え、終わったら `record <ID> <gate> --verdict … --by … --tree <控えたID>` で記録する（review、verify、ux では `--tree` が必須）。
2. verifier には仕様（受け入れ基準）と作業場所を渡す。実装者と同じ実行を検証役に使わない。
   verifier と ux-designer には、受け入れ試験（`tests/acceptance/`）と記録（`docs/verification/`）を**新しいファイルとして**足すよう伝える。既にあるファイルの書き換え、削除、名前の変更は、製品コードの変更と同じ扱いになり、レビューと検証がやり直しになる（2回目の記録は別のファイル名で置く）。
3. 指摘が出たら実装担当に戻す。**同じ作業で3回戻っても通らなければ**、仕様か設計に問題がある。仕様を見直し、必要なら `po-board.md` の「止まっていること」に書く。
4. 基準を満たせないと分かったら、基準を黙って緩めない。緩めるなら `docs/decisions.md` に理由を書く。

### G5 統合する

0. `needs_windows: true` の作業単位は、ブランチを push し、POのWindowsのPCで `python scripts\local_ci.py --ref origin/<ブランチ>` を実行してもらう。結果のファイル（`.cycle\ci\` の下）をPCのフォルダから読み、`python scripts/cycle.py record-ci <ID> --result <ファイル>` で取り込む。GitHub上の自動テストは手で起動したときだけ走る（D-031）。
1. `scripts/cycle.py status <ID>` で統合できることを確かめ、作業ツリーでコミットし、`scripts/cycle.py merge <ID>` で `main` に取り込む。その後 push し、作業ツリーを片付ける。
   取り込まれるのは作業ツリーの HEAD のコミット。作業ツリーはブランチの上に置いたままにする（切り離さない）。本体のチェックアウトは `main` で、未コミットの変更が無い状態にしておく。競合や、取り込んだ後の確認の失敗で取り込めなかったときは、スクリプトが本体を元に戻す。作業ツリー側で `main` を取り込んで直し、ゲートをやり直す。
   `merge` は、取り込んだ後の確認が終わるまで掛かる。道具の時間切れを十分に長く取り、途中で打ち切らない。途中で止まった場合は、push の前に `scripts/cycle.py status` を見る。「注意: 前回の統合が途中で終わっている」と出たら、確認の済んでいない取り込みが `main` に残っているので、`merge` をもう一度実行して戻す。
2. `docs/plan/roadmap.md` の状態、`CHANGELOG.md`、設計の決定があれば `docs/decisions.md` を更新する。
3. リリースの区切りなら release-manager に文書と配布物の確認を頼む。

### G6 POに報告する

`docs/plan/po-board.md` を次の形で更新する。POは実装の細部を見ない。判断に必要なことだけ書く。

```
## 現在地
（どのリリースの、どこまで終わったか。1〜2文）

## 今回できたこと
- （利用者から見て何ができるようになったか。実測値を添える）

## 次にやること
- （作業単位のIDと一言）

## 既定で進めた判断
- （オーケストレーターが決めたこと。POが覆せるように理由を一言）

## POの判断が必要なこと
- （無ければ「なし」）

## 止まっていること・リスク
- （無ければ「なし」）
```

## してはいけないこと

- 実装した本人に検証させる。
- 検証で測れなかった基準を合格として扱う。
- テストを通すために許容差を広げる、テストを消す。
- POの判断が必要なこと（公開、製品名、ライセンス変更、費用）を勝手に実行する。
- 仕様に無い機能を足す。必要だと思ったら roadmap に書いて次に回す。
- `scripts/cycle.py merge` を通さずに `main` へ取り込む。
