### 基準6: `tree_id` の比較（main 版と W2 版）

一時リポジトリ（実行できる印のファイル、リンク、無視の対象、強制追加した無視の対象のファイルを含む）で、
19 の状態を `core.fileMode` の true と false の両方に当てた。「= HEAD」は、コミットのツリーと同じIDになったか。

- `core.fileMode=true`: 18 の状態（変更なし、変更、新規、実行できる新規、削除、名前の変更（mv、git mv）、印だけの変更（付ける・外す）、
  無視の対象の追加、強制追加したファイルの変更と削除、索引だけの変更、assume-unchanged と skip-worktree の付いた変更、
  リンクの付け替え、`rm --cached`（無視の対象でない）、印の変更と中身の変更）で、main 版と W2 版のIDが同じ。
- 違ったのは1つだけ: 強制追加した無視の対象のファイルを `git rm --cached` した状態。main 版は「変更あり」、W2 版は HEAD と同じ。
  W2 版はディスクの上の内容（ファイルはある）を表していて、`merge` が取り込む HEAD の内容とも一致する。確認した内容と
  取り込む内容が食い違う方向ではないので、緩みではない（取り消しの索引を残したまま統合できるようになる、という違いはある）。
- `core.fileMode=false`: main 版は、変更の無い状態でもコミットのツリーと一致しない（実行できる印が外れて数えられる）。
  W2 版は、変更の無い状態、印だけの変更で HEAD と一致し、ほかの変更は `fileMode=true` のときと同じく検出する
  （印を引き継ぐので、印の付いたファイルを変えたときのIDは true のときと違う。git 自身の決まりと同じ）。
- Windows の既定の模擬: W2 を `core.fileMode=false`、`core.symlinks=false`、`core.autocrlf=true` で取り出し、
  全ファイルの実行できる印を外した。W2 版 `cb42e00…`（コミットと一致）、main 版 `6ccb25c…`（不一致）。
  実装者の言う「W1 の求め方がコミットのツリーと違うIDを返す」を再現した。
- どの状態でも、作業ツリーの索引は変わらなかった（決まり9）。

## 見つけた問題

1. **重大: 試験を絞った実行が合格として記録され、取り込まれ、使い回される**
   - 再現: 全体では落ちるコミット（一時リポジトリ。`test_value` が落ちる）で
     `PYTEST_ADDOPTS="-k test_env" python scripts/local_ci.py --no-fetch --ref <コミット>` → 終了コード 0、
     `verdict: pass`（通過1件）。`--deselect` でも同じ。結果には絞ったことが何も残らない（件数が少ないだけ）。
     Windows の結果として `record-ci` すると `windows: pass` を記録する。その後、`PYTEST_ADDOPTS` を付けずに
     `--force` 無しで同じコミットを実行すると、「同じ内容を、同じ環境で確かめた結果が既にある」と表示して実行せず、
     終了コード 0（定期実行も合格を示し続ける）。試験: `test_c3_a_run_with_only_some_tests_selected_does_not_make_a_pass`。
   - 原因: `run_check` が呼び出し元の `PYTEST_ADDOPTS` を残して JUnit のオプションを足している（実装の試験
     `test_check_gets_the_report_file_outside_the_checked_content_and_no_input` が「利用者のオプションは残す」と確かめている）。
     使い回しの条件（`identity`）と `record-ci` は、利用者のオプションの有無を見ない。
   - 直し方の案: 呼び出し元の `PYTEST_ADDOPTS` を引き継がない。引き継ぐなら、有無（真偽だけ）を結果に入れ、
     その結果を合格として使い回さず、`record-ci` でも合格として取り込まない。
   - 参考: W1 からの `cycle.py check` も `PYTEST_ADDOPTS` を引き継ぐ（同じ形の穴）。ただし出力がログに残り、
     使い回しも無い。W2 の範囲外なので、H2 で扱うかをオーケストレーターが決める。
2. 軽微: Linux / macOS では、時間切れ（`--timeout`）とプロセスだけへの中断（SIGTERM など）で止まるのは
   `scripts/check.py` だけで、その先の pytest が動き続ける（親が 1 になり、消した場所で試験を最後まで実行する）。
   後始末と合否には影響しない（取り出した場所は作り直されず、結果は error のまま）。端末の Ctrl-C（まとまり全体への合図）では残らない。
   Windows は `taskkill /T` で先まで止める。8章の「確認のプロセスは止める」と合わない。
   再現: `test_c1_the_tests_do_not_keep_running_after_a_timeout`（xfail、Linux / macOS だけ）。直し方の案: 新しいプロセスのまとまりで起動し、まとまりごと止める。
3. 軽微: `record-ci` は `mode: current`（作業フォルダで確かめた）結果も取り込む。無視の対象のファイル（`*.csv` など）に
   助けられた合格でも、ツリーは同じで `dirty: false` になる。再現: コミットに無い `data.csv` を読む試験を作業ツリーに置き、
   `--ref` では不合格、`--current` では合格。その `--current` の結果を `record-ci` が `windows: pass` として記録した。
   既存の check のゲート（作業ツリーで実行）と同じ強さなので重大にはしない。8章の手順は `--ref` を使う。直し方の案: `record-ci` で `mode` が `checkout` のものだけを取り込む。
4. 軽微: 使い回しの条件に文字コード（`encoding.locale`、`utf8_mode`）が入っていない。`PYTHONUTF8=0` で合格した結果を、
   `PYTHONUTF8=1` の実行が使い回した（逆も同じ）。Windows では、UTF-8 に設定した端末の合格が、素の端末（cp932）の実行で示される。
5. 軽微（範囲5、受け入れ基準の外）: `CLAUDE.md` のコマンドと `milestone-cycle` スキルに、`local_ci.py` と `record-ci` が書かれていない。
6. 記録だけ: 実行する `local_ci.py` は、作業中のフォルダのもの（確かめるコミットのものではない）。どの版で確かめたかは結果に残らない。

## Windows の結果を受け取ったときに確かめること（基準5）

POが `python scripts\local_ci.py --ref origin/W2` を実行した結果のファイルについて、次のすべてを満たせば合格と言える。

- ファイル名が `<時刻>-windows-<コミットの先頭10桁>.json` で、UTF-8 として読め、改行が LF だけ（CR が無い）。
- `schema` が 1、`kind` が `local-ci`、`mode` が `checkout`（`--current` の結果は受け取らない。問題3）、`ref` が `origin/W2`、`dirty` が false、`changed` が空。
- `commit` が、POが実行した時点の `origin/W2` の先頭（push したコミット。先に控えておく）と一致し、`tree` が Linux で求めた
  `git rev-parse <commit>^{tree}` と一致する（決まり9の、実機での確かめ。違えば `content_mismatch` の error になっているはず）。
- `os.system` が `Windows`、`python.version` が 3.11 以上。
- `encoding.locale` が `cp932`、`encoding.utf8_mode` が false（文字コードの設定を足していない素の状態で走ったこと。問題4のため、UTF-8 の端末の結果では代わりにならない）。
- `check.returncode` が 0、`check.timed_out` が false、`check.seconds` が数分（数秒なら、試験がほとんど走っていない）。
- `tests.failed` と `tests.errors` が 0、`failed` が空、`verdict` が `pass`、`reason` が `ok`。
- `tests.total` が、同じコミットの Linux の件数とほぼ同じ（`fee52d2` で 964。この検証の受け入れ試験を足したコミットなら 29 件増える）。
  スキップの差は OS だけの試験の分（数件）まで。大きく少なければ、試験を絞った実行（問題1）を疑い、合格にしない。
