## 見つけた問題

### 3. 軽微: 記録の pid が大きすぎると、起動が例外で落ちる（POSIX）

- 内容: `read_last_run` は pid を正の整数かどうかだけ見る。`pid_alive` の `os.kill(pid, 0)` は、C の int に入らない
  pid（2^31 以上）で `OverflowError` を出し、捕まえていない（捕まえるのは `ProcessLookupError` と `OSError`）。
  前回のポートが使用中のときだけ `pid_alive` が呼ばれるので、そのとき起動がトレースバックと終了コード 1 で落ちる。
- 影響: 記録はアプリ本体が自分の pid（Linux は最大 2^22）を書くので、壊れたときか人が書き換えたときだけ。
  記録を消すか `--port` を付ければ起動できる。Windows は ctypes が値を切り詰めるので落ちない（見込み。未確認）。
- 再現: 設定の場所の `last-run.json` を `{"port": P, "pid": 2147483648}` にし、P をほかのプログラムが使っている
  状態で `circuit-sim --no-browser`。試験は `test_a0_fix4_restart_lastrun.py::test_huge_pid_in_the_record_does_not_crash`
  （xfail。POSIX では strict）。
- 案: `read_last_run` で pid の範囲を絞る（例 2^31 未満）か、`pid_alive` で `OverflowError`・`ValueError` を
  「分からない」（動いているとみなす）にする。

### 4. 軽微: 記録の名前が名前付きパイプ（FIFO）だと、起動が止まる（POSIX）

- 内容: `read_last_run` の `read_text` が、書き手が来るまで待ち続ける。URL も誤りも出ず、`--port` を付けても
  同じ（`--port` の有無にかかわらず記録を読む）。設定ファイル（`settings.json`）と合言葉（`token`）が同じ形の
  ときは起動する（0.64 s、2.11 s）ので、記録だけ守りが無い。
- 影響: 設定の場所は本人だけが書ける（0700）ので、そのような物を置けるのは本人だけ。利用者がふつうに起こす
  形ではない。
- 再現: `mkfifo <設定の場所>/last-run.json` → `circuit-sim --no-browser --port <空き>`。15 秒たっても URL が出ない。
  試験は `test_a0_fix4_restart_lastrun.py::test_fifo_record_does_not_hang_the_start`（xfail、strict、POSIX だけ）。
- 案: 設定ファイルと同じ読み方（本物のファイルかを確かめてから、大きさを決めて読む）にする。

### 5. 軽微: 起動直後の画面で、保存し直せてお知らせが自動で消えると、フォーカスが本文に落ちる

- 内容: 改善2 は「閉じる」と Delete の道だけ。保存し直せてお知らせが自動で消える道（改善1）では、フォーカスを
  移さない。起動直後の画面では帯ごと消えるので、帯の中にフォーカスがあると本文（body）に落ちる。次の Tab は
  ヘッダーの「開く」。
- 起きる形: お知らせの文は「直した後に好みを1つ変えると保存し直し」と案内する。帯の開閉も好みの保存なので、
  キーボードの利用者が直した後に帯の見出しで Enter を押すと、保存でき、帯が消え、フォーカスが落ちる。
- 照らしたもの: AC-1-5（フォーカスが見えない位置に入らない）、UX 確認3回目の改善2 と同じ種類。
- 影響: 行き止まりではない（次の Tab で戻れる）。A1 で行に「もう一度」を足すと（UX 確認3回目の決めごと1）、
  押した場所（行の中）が消えるので、この道が主な道になる。A1 の仕様に入れてほしい。
- 再現: 実際の Chrome。起動直後の画面で設定ファイルに書けなくし（設定ファイルの名前をフォルダにする）、テーマを
  替える → 帯が出る → 書けるように戻す → 帯の見出しにフォーカスして Enter。
  試験は `test_a0_fix4_browser.py::test_auto_cleared_save_notice_on_the_start_screen_keeps_focus_visible`（xfail、strict）。
- 案: お知らせが消えて帯ごと消えるとき（理由を問わず）、フォーカスが帯の中にあれば「ファイルを選ぶ…」へ移す。

### 観察（問題としない）

- 前回のポートが使用中で、前回のプロセスが無いとき、そのポートで待ち受けているかを確かめるために、1回つなぐ
  （ほかのプログラムに、何も送らない接続が1本届く）。
- 記録の名前がフォルダのとき、記録を書けないことを黙る（次の起動で前回のポートに戻れないだけ）。
- 引数が `--` だけのとき「知らないオプションです: --」、空の文字列のとき「ファイルを受け取りません（）」と、
  括弧の中が空になる。どちらも利用者がふつうに起こす形ではない（UX の確かめに任せる）。
- 1c のとおり、止める合図から 2 秒で閉じ終わらない接続は打ち切る（説明どおり）。

### 手順の誤り（記録しておく）

- 起動の時間を測る道具（`--port` を付けずに起動する）を、1回だけ名前空間の外で流し、共有の機械の 28470 を
  4 回、各 2 秒ほど使った。毎回 28470 で起動できた（ほかに使っている者はいなかった）。その後は名前空間の中で流した。
- 製品を壊した写し（M9: 記録を書かない）で起動し直しの受け入れ試験を流したとき、前回のポートに戻れず、28470 で
  数秒起動した。受け入れ試験が 28470 番台に触るのは、製品が前回のポートに戻れないとき（試験が落ちるとき）だけ
  （実装の試験 `test_app_cli.py` の起動し直しの試験も同じ）。
- UX の確かめの道具が途中で落ちたとき、アプリ本体が1つ残った（uid 4242、`/tmp/a0-verify-5/venv` の circuit-sim、
  127.0.0.1:48211、設定の場所は `/tmp/a0-verify-5/cfg-4242-wk86k5_b`）。止める操作はこの実行では許されなかったので、
  残したまま報告する。28470 番台ではないので、ほかの担当の確かめには触らない。

## 実装担当が変えた受け入れ試験についての判断と、書き直し

`tests/acceptance/test_a0_fix3_stop_stale_sddl.py`（3回目の検証の成果物）を、実装担当が 56c95fc で変えていた:

- 判断: 妥当。xfail の2つは直っていて、strict なので残すと XPASS で落ちる（外すのが3回目の記録の決まりどおり）。
  差し替え先の関数が無くなったので、Windows の分かれ目そのものを強制するのは筋がよい。確かめる強さも落ちていない:
  止める手順に Windows だけの RST の印を戻した写し（M1）では、実装担当の形の試験も落ちる。
- 足りなかったこと: 強制が効いたことを見ていない（効いていなければ POSIX の経路を2回見るだけになる）、読む速さが
  1通り、冒頭の説明が古い。
- 書き直した行（今回に限り許された）:
  - 冒頭の説明（1〜24 行）: RST をやめた後の形に書き直し、3回目と4回目のどちらの記録かを書いた。SDDL の項も、
    直ったので印を外したことに書き直した。
  - `test_slow_reader_gets_the_whole_asset_with_the_windows_reset_branch` を
    `test_slow_reader_gets_the_whole_asset_with_the_windows_path` に改め（178〜200 行）、読む間隔 0・2 ms の2通りに
    し、待ち受けのソケットに SO_REUSEADDR が付いていないこと（強制が効いたこと）を確かめる行を足した。読む行
    （217 行）を、その間隔で読むようにした。差し替えの理由を説明に書いた。
  - SDDL の `)` の例（`SDDL_PAREN_IN_STRING`、312〜332 行）に、1d の 16 通り（文字列の読み方の角と、項目の並びの
    後ろの読み残し。対照4つを含む）を足し、試験の関数に説明を足した（355 行）。
