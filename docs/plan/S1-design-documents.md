# S1: 設計書の整備（要求仕様、基本設計、用語集、精度と分解能）

担当: ux-designer（要求仕様）、control-engineer（用語集、精度と分解能）、オーケストレーター（基本設計、文書の体系）

## 背景

PO の指示（2026-11-16）: 今後の保守を考え、基本設計までの設計書を作っておく。ユースケースやシナリオを含める。
あわせて PO から、電気・電子の専門用語を正しく押さえているか、分解能をどこまで許容する設計か（根拠つき）、の問いがあった。

いまある文書は、全体設計の要約（`architecture.md`）、アプリの骨格（`app-design.md`）、画面仕様、デザインの基準、ハーネスの設計、決定記録、作業単位ごとの仕様。
足りないのは次の4つ。

- 利用者・ユースケース・シナリオ・要求を1か所にまとめた文書
- 保守する人が全体を追える基本設計書（構成、データ、処理、インターフェース、拡張の口）
- 専門用語の対応表。画面と文書の言葉の一部が、現場の標準の用語からずれている（「段差」「積分の飽和を防ぐ処理」「出どころ」など）
- 分解能と精度を、どこまで許容するか、なぜかを書いた文書（いまは決定記録 D-021・D-036 と受け入れ基準に散らばっている）

## 受け入れ基準

1. ユースケースが、いまのロードマップ（v0.1〜v0.5 と構想）の「利用者ができること」をすべて覆い、それぞれに利用者、きっかけ、前提、基本の流れ、別の流れ（不足・エラー・未達）、結果、対応するリリースがある。
2. シナリオが3本以上あり、うち1本以上は失敗からの立ち直り（単位の取り違え、値の不足、目標未達など）を含む。
3. 機能要求と非機能要求に番号があり、ユースケース、作業単位、受け入れ基準または試験への対応が表で追える。
4. 基本設計が、実装（main と、統合前の E1b・A0 のブランチ）と食い違わない。食い違いや未実装は「予定」と明記する。事実でないことを書かない。
5. 精度と分解能の文書に、設計値ごとの根拠（測った値、決定番号、出典）と、実機の制御器（PWM のカウンタ、ADC のビット数）との比較、モデルに入っていないもの（量子化、デッドタイム、損失など）の一覧がある。
6. 用語集が、画面仕様とエンジンの注意に出る専門用語を覆い、標準の用語からずれた表記に是正の案がある。是正そのもの（画面仕様と文言の書き換え）は、画面の見た目の練り直し（A0r の続き）と A1 の仕様で行う。
7. `python scripts/check.py` が通る。
