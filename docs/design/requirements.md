## 1. 目的と背景

**何のための道具か。** パワーエレクトロニクスとモーター制御の設計者が、手元の設計書（仕様と回路定数）から回路と制御系のシミュレーションモデルを組み、設計目標を満たす PID ゲインを、検証つきで受け取るためのアプリ。

**背景。** 設計者は設計書を持っているのに、次の3つに時間を取られている（`app-design.md` 1章）。

1. 設計書の内容で回路がどう動くかを見るために、シミュレーションモデルを組む。
2. 設計目標（オーバーシュート、整定時間、安定余裕）を満たすゲインを、手で振って探す。
3. 結果を、根拠つきで人に渡せる資料にまとめる。

**中心の流れ。** ① 取り込む → ② 確かめる → ③ 動かす → ④ 決める → ⑤ 残す。どの段階からでも始められる。v0.1 は ② と ③、v0.2 で ④ と ⑤、v0.3 で ① が入る。

**差別化。**

- **設計目標 → ゲイン → 検証まで閉じること。** 設計目標を入れるとゲインが出て、そのゲインをスイッチングモデルで確かめた結果と、目標ごとの達成・未達が返る。満たせないときは、最良のゲインと「どの目標が、どれだけ足りないか」が返る。途中を人が別の道具でつながない。
- **使われる道具としての完成度。** 設計者は数値の正しさと根拠に厳しい。優先順位は「間違いに気づける ＞ 速く用事が済む ＞ 見た目の整い」（`app-design.md` 4章）。値には必ず単位と出典があり、不足を推測で埋めず、未達を達成と表示しない（`CLAUDE.md` 決まり4）。

**提供の形。**

| 項目 | 内容 | 根拠 |
|---|---|---|
| 動く場所 | 利用者の PC。ローカルサーバーを起動し、ブラウザで操作する。ネットワークが無くても、AI 連携以外はすべて動く | D-006、`app-design.md` 5章 |
| 配布 | 基礎機能を GitHub で配布し、商用利用を認める。いまは非公開で、公開の時期は PO が決める | D-003、D-013 |
| ライセンス | Apache-2.0（暫定）。依存は商用利用できるライセンスだけ | D-004、D-005 |
| 名前 | 未定。仮称 circuit-sim | D-012 |
| AI の位置 | 関わるのは「設計書からの抽出」と「結果の説明」だけ。計算の経路は決定的。AI が無くても、仕様 JSON を手で書けば残りはすべて動く | `CLAUDE.md` 決まり1、`architecture.md` 1章 |

### UC-01 同梱のサンプルで、はじめて動かす

- **きっかけ**: インストールした直後。手元に仕様 JSON が無い。または、自分の案件を入れる前に、道具が信用できるかを見たい。
- **前提**: インストール済み（UC-14）。ネットワークは要らない。
- **基本の流れ**: 1. `circuit-sim` を実行すると、ブラウザに起動直後の画面が開く。 2. 「サンプルから始める」の1行（RC ローパス、直列 RLC、降圧コンバータ）を選ぶ。 3. 値の一覧と回路図が出て、フォーカスは「実行」にある。 4. 実行する。 5. スコープに、既定の信号の波形が出る。
- **別の流れ**: (a) サンプルの一覧が取れない → その位置にエラーと「もう一度」。ファイルを開く側は使える。 (b) アプリ本体につながらない → 接続の帯が出て、自動でつなぎ直す。 (c) ブラウザが開かない → 端末に出る URL を開く（UC-14）。
- **結果**: 説明を読まずに、起動から3分以内に波形を見ている。
- **関係**: FR-01、FR-08、FR-17、FR-35、FR-38。AC-3-1〜3-5、AC-4-1、AC-4-8、AC-11-1。

### UC-02 仕様 JSON を開き、値と出典を確かめて直す

- **きっかけ**: 手で書いた、または人から受け取った仕様 JSON で計算したい。
- **前提**: 仕様 JSON（層A、版 0.1 か 0.2、UTF-8）。
- **基本の流れ**: 1. ファイルを選ぶか、ウィンドウにドロップして開く。 2. 計算に使われる値が、単位と出典（いまの画面の表記: 出どころ）つきで全部並ぶ。回路図にも同じ値が出る。 3. 違っている値を、その場で工学表記（`47u`、`4.7e-5`、`47 µH`）で直す。打っている間、どう読まれたかが出る。 4. 直した行に、変更の印と変更前の値が付く。元に戻せる。 5. 保存する（v0.1 はブラウザのダウンロード）。
- **別の流れ**: (a) 開けない（JSON の誤り、文字コード、版、形、テンプレート名）→ 何行目・どの項目かと、直し方が出る。開いていた仕様と結果には手を付けない。 (b) 値が不足（`null`、項目なし）→ その行が不足になり、実行できない理由と件数が出る。推測では埋めない。 (c) 単位に接頭語（`mH`、`uF`）→ 換算して読み、何をどう換算したかを知らせる。 (d) 単位の次元が違う、読めない → その行がエラーになり、書かれていた値と単位をそのまま見せて、入力し直してもらう。 (e) 読めない入力（`1,000`、`4k7`、`47U`）→ 打った文字を残し、直し方を出す。 (f) 変更前の 1000 倍以上か 1/1000 以下になる入力（m と M の取り違え）→ 打っている間に倍率を出し、確定後に注意を1件出す。止めない。 (g) 組で入れる値の片方だけ（負荷ステップの抵抗と時刻）→ 足りない側が不足になる。 (h) 保存していない変更があるまま別の仕様を開く → 確認する。 (i) 版 0.1 で制御の値が数値だけ → 項目の単位とみなして読み、そうしたことを知らせる。
- **結果**: 計算に使う値をすべて確かめてあり、不足もエラーも無い（または、どれが足りないかが分かっている）。画面で直した値の出典は「手入力」になる。
- **関係**: FR-01〜07、FR-16、FR-20、FR-38。AC-2-1〜2-7、AC-4-1〜4-9、AC-5-1〜5-7、5-9、5-10、5-15〜5-17、AC-9-2、9-4、AC-11-5。

### UC-03 シミュレーションを実行し、スコープで波形を読む

- **きっかけ**: いまの値で回路がどう動くか（起動、ステップ応答、負荷ステップの応答）を見たい。
- **前提**: 不足もエラーも無い仕様 JSON を開いている。
- **基本の流れ**: 1. 実行する（ボタン、Ctrl+Enter）。 2. 時間のかかる計算では進み具合が出る。計算中も、値の編集や波形の操作ができる。 3. 完了すると、既定の信号が単位ごとの段に出る。どの実行の、どのモデルの、どの時間刻みの結果かが、波形のそばに出る。 4. 気になる所を拡大する（ドラッグで範囲を選ぶ、ホイール、ダブルクリックで全体）。 5. カーソル A・B を置き、Δt、1/Δt、値の差を読む。読む値は、画面用に間引く前の計算結果そのもの。 6. 回路図の測定点か信号の表で、見る信号を足す、外す。
- **別の流れ**: (a) 実行できない（不足、入力エラー、ステップ数が上限を超える）→ 実行する前に、理由と直す場所が出る。上限のときは、そのまま打てる値を示す。 (b) 時間刻みが粗い → 止めずに、注意を値の行、波形のすぐ上、お知らせに出す。勧める時間刻みがあれば示す。 (c) 計算の失敗（回路の式が解けない、スイッチとダイオードの状態が決まらない、発散、メモリ不足）→ 何が起きたかと直し方が出る。直前の完了した結果は残る。 (d) 中断 → 1秒以内に止まり、途中の波形は見せない。 (e) 計算中に値を変えた → 終わった結果は「古い結果」として出る。 (f) アプリ本体が止まった、再読み込みした → UC-14 の (d)(e)。
- **結果**: 設計の判断に要る数値（オーバーシュート、整定までの時間、リプルの幅など）を、単位つきで読めている。その波形をそのまま信じてよいか（古い結果か、計算からの注意があるか）が分かっている。
- **補足**: オーバーシュートと整定時間を自動で測るのは v0.2（FR-27）。v0.1 はカーソルで読む。
- **関係**: FR-09〜11、FR-13〜19、FR-38。AC-1-2、AC-5-11〜5-13、AC-6-4、AC-7-1〜7-9、AC-8-1〜8-8、8-12〜8-20。

### UC-04 値を変えて再実行し、前の結果と比べる

- **きっかけ**: 値（ゲイン、L、C、負荷）を変えると応答がどう変わるかを見たい。
- **前提**: 1回以上、実行が完了している。
- **基本の流れ**: 1. 値を変える。スコープの結果が「古い結果」になり、どの値が違うかが出る。 2. 再実行する。表示範囲、カーソルの位置、信号の選び方は保たれる。 3. 「比較」で、前の結果が同じ色の破線で重なる。どの実行と比べているかと、値の違いが出る。 4. 最初の結果と比べ続けたいときは、比較対象を「固定」する。
- **別の流れ**: (a) 値を元に戻した → 「古い結果」が消える。 (b) 再実行が中断、失敗 → 今回の結果も比較対象も変わらない。 (c) 別の仕様を開いた → どちらも消える。 (d) 比較対象に無い信号 → UC-05 の (a)。
- **結果**: 2つの結果を同じ時間軸と縦軸で見比べ、どの値を変えた結果かを取り違えない。
- **関係**: FR-17、FR-21、FR-38。AC-7-7、AC-8-9、8-10、8-15、8-24、AC-11-4。

### UC-05 モデルを切り替える（スイッチングモデル / 状態平均化モデル）

- **きっかけ**: リプルは要らないので応答の形を速く見たい。または、最後にリプル込みで確かめたい。
- **前提**: スイッチを含むテンプレート（v0.1 では降圧コンバータ）を開いている。
- **基本の流れ**: 1. 計算の設定の「モデル」で、スイッチングモデル（既定）か状態平均化モデル（いまの画面の表記: 平均、平均モデル）を選ぶ。 2. 時間刻みの自動の値、ステップ数、回路図のレグの描き方が、その場で替わる。 3. 再実行する。結果の説明にモデルの名前が出る。 4. 2つのモデルの結果を、比較で重ねる（UC-04）。
- **別の流れ**: (a) 状態平均化モデルに無い信号（入力電圧、入力電流、ゲート信号）を表示していた → 行は同じ位置に残り、「この結果にはありません」と出る。スイッチングモデルに戻すと、同じ色で戻る。 (b) 状態平均化モデルの前提（入力の電源にインピーダンスが無い）に合わない回路 → スイッチングモデルで計算するよう注意に出す（D-038）。 (c) 3つ目の「理想」モデル（トルク源と電流応答の一次遅れ）は将来（時期は未定。選択欄は、足せる形にしてある）。
- **結果**: 目的に合ったモデルで計算し、見ている波形がどちらのモデルのものかを取り違えない。
- **関係**: FR-12、FR-19〜21、FR-38。AC-5-14、AC-6-8、6-10、AC-8-22、8-25、8-26。E1b の基準4・5。

### UC-06 波形と仕様を書き出す（CSV、JSON）

- **きっかけ**: 実測の波形と重ねたい。表計算や自分のスクリプトで処理したい。直した仕様 JSON を人に渡したい。
- **前提**: 完了した結果がある（CSV）。仕様 JSON を開いている（保存）。
- **基本の流れ**: 1. スコープの「CSV…」で、信号（表示中 / すべて）と範囲（表示中 / カーソル A〜B / 全体）を選ぶ。行数と大きさの見積もりが出る。 2. 書き出す。間引かず、補間せず、SI 単位（接頭語なし）で、見出しに単位が付く。 3. 仕様は「保存」で JSON にする（UC-02）。
- **別の流れ**: (a) 行数が表計算ソフトの上限を超える → 注意を出す。止めない。 (b) 古い結果、または注意の付いた結果を書き出す → そのことを1行添える。 (c) 書き出せない → 理由と直し方が出る。 (d) 計算の都合で足した内部の信号は、「すべての信号」にも入れない。
- **結果**: 画面で読んだ値と同じ値がファイルにある。同じ仕様 JSON をコマンドラインで書き出した CSV と一致する。
- **関係**: FR-06、FR-22、FR-38。AC-5-9、AC-8-11、8-21、8-23、8-25。

### UC-07 設計目標から PID ゲインを求める

- **きっかけ**: 手でゲインを振るのをやめて、設計目標を満たすゲインを受け取りたい。
- **前提**: 不足の無い仕様 JSON。設計目標（オーバーシュート、整定時間、位相余裕など）。
- **基本の流れ**: 1. 設計目標を入力する。 2. ゲインを求める計算を始める。進み具合が見え、中断できる。 3. 道具は、解析式で初期値を決め、状態平均化モデルで評価関数を最小化し、線形化した一巡伝達関数（開ループ）の安定余裕を制約にして、スイッチングモデルで確かめる（`architecture.md` 5章）。 4. ゲイン、目標ごとの実測値と達成・未達、安定余裕が出る。 5. 求める前と後の応答を重ねて見る。 6. ゲインを受け入れると仕様に入り、道具が求めた値だと分かる出典が残る（書き方は A2 で決める）。
- **別の流れ**: (a) 目標を満たせない → UC-08。 (b) 値の不足 → 始める前に、理由と直す場所が出る。 (c) 中断 → 仕様のゲインは変えない。 (d) 状態平均化モデルとスイッチングモデルで結果が違う（三角波キャリアの測定点による定常のずれなど。D-047）→ 差を隠さない。どちらで判定するかは E2 の仕様で決める。
- **結果**: 目標を満たすゲインと、その検証（どのモデルで、どの値が、目標に対していくつか）が手に入る。同じ仕様と目標からは、同じゲインが出る。
- **補足**: いまあるのは、降圧コンバータの電圧モード PID の初期ゲインを解析式で決める関数（`circuit_sim/tuning/initial.py`。E1b のブランチ）。位相余裕の目標に届かないときは、理由と最良の候補を返す。画面からは使えない。
- **関係**: FR-15、FR-23、FR-24、FR-26、FR-27。ロードマップの E2・A2 の基準。

### UC-08 目標を満たせないとき、何がどれだけ足りないかを知る

- **きっかけ**: UC-07 の結果が未達だった。
- **前提**: UC-07 が終わっている。
- **基本の流れ**: 1. 未達が、言葉と数値で示される（どの目標が、目標いくつに対して、いくつで、どれだけ足りないか）。色だけに頼らない。 2. 最良のゲインと、そのときの応答と安定余裕を見る。 3. 次の手を選ぶ: 目標を緩める。回路定数や制御周期を見直す（UC-02 → UC-07）。デューティ比が上下限で飽和していないかを波形で確かめる（UC-03）。
- **別の流れ**: (a) 一部の目標だけ未達 → 達成した目標と未達の目標を分けて示す。 (b) 安定な解が無い → そう示す。「安定」と言うのは、丸めで結論が変わらない余裕があるときだけ（初期ゲインの設計の決まり。D-057）。 (c) 探した範囲の端で決められない → 理由と、範囲を制限したことを結果に残す（D-057）。
- **結果**: 未達を達成と取り違えない。設計を変えるか、目標を変えるかの判断材料を持っている。

### UC-09 結果を根拠つきのレポートにして残す

### UC-10 設計書（Word / PDF / Excel / テキスト）から仕様を取り込む

- **きっかけ**: 仕様 JSON を手で書かずに、設計書から始めたい。
- **前提**: 設計書のファイル。AI 連携が使える（最初の実装は、ローカルの CLI を呼ぶ方式。D-008）。
- **基本の流れ**: 1. 設計書を開く。 2. 道具が、設計書をコードで「位置ラベルつきの共通テキスト」に変える。元のファイルは AI に渡さない。 3. AI に送る内容を、送る前に画面で示す。利用者が確かめて送る。 4. AI が仕様 JSON（層A）を埋める。値ごとに出典（設計書の位置）が付く。書かれていない値は `null` のまま残る。 5. コードが仕様を検証し、確認の画面に並べる（UC-11）。
- **別の流れ**: (a) 読めないページ（スキャン PDF、図）→ 「読めなかったもの」として一覧に出る。 (b) AI 連携が使えない、利用者が送らない → 取り込みはできない。仕様 JSON を手で書けば、残りはすべて動く。 (c) AI の出力が仕様の形に合わない → コードの検証で弾き、理由を示す。 (d) 互換文字の単位（㎌、㏀、全角）→ 正規化するかどうかは I1 で決める（D-037）。 (e) 同じ入力をもう一度取り込む → 応答のキャッシュから、同じ結果が出る。
- **結果**: 記載のある値が、出典つきで仕様に入っている。記載の無い値と読めなかった箇所が、そうと分かる形で残っている。
- **関係**: FR-29、FR-30。ロードマップの I1・I2 の基準（記載のある値の正解率 95% 以上、作り話ゼロ）。

### UC-11 取り込んだ値の出典を確かめ、足りない値を埋める

- **きっかけ**: UC-10 の直後。
- **前提**: 取り込んだ仕様が、確認の画面に並んでいる。
- **基本の流れ**: 1. 値の行から、設計書の該当箇所を開いて見比べる。 2. 合っていれば確認済みにする。違っていれば直す（出典は「手入力」になる）。 3. 不足の値を、データシートなどを見て入力する。 4. 不足が無くなると、実行できる（UC-03）。
- **別の流れ**: (a) 読めなかった箇所に値があった → 人が見て入力する。 (b) 単位や桁の取り違え → UC-02 と同じ仕組みで気づける。 (c) 設計書の中で値が食い違う（本文と表）、確認していない値が残ったまま実行する → 扱いは I2・A3 の仕様で決める（8章 U-8）。どちらの場合も、道具が黙って片方に決めない。
- **結果**: すべての値に、設計書の位置か「手入力」の出典がある。人が確かめた値と、まだの値が区別できる。
- **関係**: FR-02〜05、FR-31。ロードマップの A3 の基準（読めなかったページが画面に出る）。

### UC-13 コマンドラインで計算する

- **きっかけ**: 条件を振ってまとめて回す。自動の確認に組み込む。画面を開かずに結果だけ欲しい。
- **前提**: 仕様 JSON。Python の環境。

- **結果**: 画面と同じ判定、同じ数値が、スクリプトから得られる。
- **補足**: CSV の見出しの単位（D-042）と、注意・エラーの番号と英語の文面は E1g で入る（予定）。
- **関係**: FR-04、FR-05、FR-09、FR-22、FR-39、FR-40。`tests/test_console_encoding.py`、`tests/acceptance/test_e1a_units_limits.py`、AC-8-11。

### UC-14 インストールする、起動する、止める、更新する

- **きっかけ**: 使い始める。作業を終える。新しい版が出た。
- **前提**: Python 3.11 以上。Node.js は要らない（D-041）。
- **基本の流れ**: 1. 1行でインストールする（v0.5 の目標。いまはリポジトリから `python -m pip install -e ".[dev]"`）。 2. `circuit-sim` を実行する。アプリ本体が 127.0.0.1 で待ち受け、既定のブラウザに作業画面が開く。 3. 作業する。 4. 端末で Ctrl+C を押して止める。 5. 新しい版に更新する（手順は R1 で決める）。
- **別の流れ**: (a) ポートが使われている → 前回のポート（設定の場所に残した前回の起動の記録）、既定の 28470、28471〜28479 の順に試し、どれも使えなければ空いているポートを使う。`--port` で指定したポートが使えないときは、理由を出して終わる（D-050、D-061）。 (b) ブラウザが開かない、`--no-browser` → 端末に起動コードつきの URL が出る（1回だけ、5分以内に使える。Enter で新しい URL。D-056）。 (c) 保存していない変更があるまま Ctrl+C → 1回目は止めずに知らせ、10秒以内にもう一度押すと止まる。 (d) アプリ本体が止まった → 画面に接続の帯が出る。波形と値は読める。起動し直すと、画面が持つ仕様と編集を送り直して続ける（結果は消える）。 (e) ブラウザを再読み込みした → アプリ本体が動いている間は、仕様、編集、結果が戻る。 (f) 設定を保存できない → 知らせる。その画面では使い続けられる。
- **結果**: 利用者の PC の中だけで動き、止めても、つなぎ直しても、作業を失わない。

### UC-15 言語とテーマ、表示の好みを変える

- **きっかけ**: 英語で使いたい。暗い部屋で使う。波形を広く見たい。
- **前提**: 作業画面が開いている。
- **基本の流れ**: 1. ヘッダーで、言語（日本語 / English）とテーマ（明 / 暗）を切り替える。 2. 再読み込みなしで、その場で替わる。編集中の入力、表示範囲、カーソルは変わらない。 3. 仕切りの位置と、領域のたたみ方を変える。 4. 次に起動したときも同じ。

### SC-1 降圧コンバータの負荷ステップの応答を見て、ゲインを見直す

三浦さんは電源の設計者。産業機器向けの、入力 24 V、出力 12 V、スイッチング周波数 100 kHz の同期整流の降圧コンバータを担当している。SPICE 系のシミュレータとオシロスコープを毎日使う。

**v0.1 でできる範囲**

1. インストールして `circuit-sim` を実行する。起動直後の画面に「降圧コンバータ 24 V → 12 V、100 kHz」のサンプルがあり、自分の案件と条件が近いので、これを選ぶ。
2. 値の一覧に、Vin 24 V、L 47 µH、C 100 µF、R_load 6 Ω、f_sw 100 kHz、PID のゲインが、単位と出典つきで並ぶ。回路図で、同期整流のレグと、PID から PWM への経路を確かめる。
3. 実行する。スコープに出力電圧とインダクタ電流の起動の波形が出る。波形のそばに、モデル（スイッチングモデル）と時間刻み（50 ns。スイッチング周期の 1/200）が出ている。
4. 負荷ステップ（負荷急変）を入れる。R_load_step に `3`、t_load_step に `5m` と打つ。片方だけ入れた時点では、もう片方が「不足」になり、両方入れると消える。回路図の負荷抵抗の下に「→ 3 Ω、t = 5 ms」と出る。終了時刻は自動なので、ステップの後の応答まで計算に入る。
5. 再実行する。ステップの前後を拡大し、カーソル A をステップの時刻、B を出力が戻った点に置いて、電圧の落ち込みと、戻るまでの時間を読む。
6. 落ち込みが大きいので Kp と Ki を上げて再実行し、「比較」で前の結果と重ねる。どのゲインを、いくつからいくつに変えた結果かが、波形のそばに出ている。
7. ゲインを何度も振るので、状態平均化モデルに替えて速く回す（計算ステップ数は約 1/20）。良さそうなゲインが見つかったら、スイッチングモデルに戻して、リプル込みで確かめる。
8. CSV を書き出して、後で実機の測定と重ねる。仕様 JSON を保存する。

v0.1 の限界: ゲインは人が振る。落ち込みと整定までの時間は、カーソルで読む。位相余裕は出ない。

**v0.2 で続く範囲（予定）**

9. 設計目標を入れる（例: オーバーシュート 5% 以下、整定時間 1 ms 以下、位相余裕 45° 以上）。
10. ゲインを求める。目標ごとの実測値と達成・未達、安定余裕が出る。求める前と後の応答を重ねて見る。
11. レポートを書き出して、設計審査に出す。

通るユースケース: UC-14、01、02、03、04、05、06（v0.1）。UC-07、09（v0.2）。

### SC-2 失敗からの立ち直り: 単位の取り違え、値の不足、粗い時間刻み

岡田さんは評価の担当。入力フィルタの共振を見るために、設計者から聞いた定数で、直列 RLC の仕様 JSON を手で書いた。SPICE の書き方に慣れている。

1. **接頭語つきの単位。** L を `{"value": 1, "unit": "mH"}` と書いていた。開くと L の行は 1 mH と出て、お知らせに、接頭語の付いた単位を換算して読んだこと（L: 1 mH → 1e-3 H）が出る。接頭語を読み飛ばして 1 H で計算することは、どの経路でも起きない（E0 の独立検証で見つかった不具合。D-018）。
2. **値の不足。** C は聞きそびれて `null` にしてあった。C の行が「不足」になり、実行は押せず、そばに「不足 1 件」と出る。件数を押すと C の行に移る。道具は値を推測で埋めない。設計者に確かめて `10u` と打つと、「= 10 µF（1e-5 F）」と読まれたことが出て、不足が消える。
3. **m と M。** 実行して減衰振動を見た後、抵抗を 1 Ω から 500 mΩ に下げたい。SPICE の癖で `500M` と打つと、確定する前に「= 500 MΩ（5e8 Ω）」と、変更前の 500,000,000 倍であることが注意の記号つきで出る。`500m` と打ち直す。気づかずに確定しても、お知らせに注意が1件残り、「この画面では m はミリ、M はメガです」と書いてある。計算は止めない（意図した値かもしれないため）。
4. **大文字と小文字、µ。** `10U` や `5v` は読めない入力として、打った文字を残したまま直し方が出る。マイクロは `u`、`µ`、`μ` のどれでも読む。
5. **粗い時間刻み。** 長い時間を見たくて終了時刻を 20 ms に、計算を軽くしようと時間刻みを `1m` にした。実行する前に、時間刻みの行とお知らせに注意が出る。実行は止まらず、波形のすぐ上にも同じ注意と、勧める時間刻みが出る。時間刻みを空欄に戻すと、自動の値に戻る。
6. **細かすぎる時間刻み。** 逆に時間刻み 1 ns、終了時刻 1 s にすると、ステップ数が上限（2000万）を超える。実行する前にエラーになり、「時間刻みを変えないなら終了時刻は 20 ms まで、終了時刻を変えないなら時間刻みは 50 ns 以上」と、そのまま打てる値が出る。

いまの時点で確かめられること: 1・2・5・6 の判定は、エンジンとコマンドラインで実装済み（UC-13）。たとえば 5 の仕様では、コマンドラインに「h を 3.14e-05 s 以下（1周期 20 点以上）にする」と出る。2 は「計算できません。値が入っていないパラメータ: ['C']」で終了コード 2。画面は A0（数値の入力部品）と A1。
気づいた限界: 2 のように、開いたときに不足だった項目には比べる元の値が無いので、倍率の注意（3）は出ない。頼りは「どう読んだか」の表示だけになる（8章 U-10）。

通るユースケース: UC-02、03、13。

### SC-3 目標を満たせないとき、何を見て次にどうするか（v0.2、予定）

SC-1 の続き。三浦さんは、部品の費用を下げるために出力コンデンサを小さくして、同じ設計目標でゲインを求め直す。

1. 結果は「未達」。どの目標が、目標いくつに対して、いくつで、どれだけ足りないかが、言葉と数値で出る。達成した目標は、達成と分けて出る。色を見なくても読める。
2. 見るもの: (a) 最良のゲインでの応答（スイッチングモデル）。 (b) デューティ指令（操作量）が上下限で飽和していないか。 (c) 位相余裕とゲイン交差周波数。制御周期に対してゲイン交差周波数が高すぎないか（検出から操作量の反映までに、演算遅れ 1 制御周期がある）。
3. 次の手を選ぶ。目標を緩めて求め直す。または、コンデンサを戻す、制御周期を上げるなど、回路の値を見直して求め直す。前の結果と重ねて、どちらが近いかを比べる。
4. 未達のままレポートにするなら、未達と、足りない量がそのまま載る。受け取ったレビューの人が、達成と読み違えない。

この画面は A2 で設計する。エンジンの側の決まりは先にある: 満たせない目標には、最良のゲインと「どの目標がどれだけ未達か」を返す（`architecture.md` 5章）。初期ゲインの設計は、位相余裕に届かないときに理由と最良の候補を返し、境目を「満たす」「安定」と言わない（D-057、D-059）。

通るユースケース: UC-07、08、03、04、02、09。

### SC-4 設計書から取り込み、読めなかった箇所を人が埋める（v0.3、予定）

高木さんは、別の人が書いた設計書を引き継いだ。手元にあるのは、Word の設計書（本文に入出力の仕様）、Excel の定数表、インダクタのデータシート（紙をスキャンした PDF）。

1. 3つのファイルを開く。道具が、中身を位置ラベル（ページ、表、セル）つきのテキストに変える。
2. AI に送る内容が画面に出る。社外に出してよい中身かを確かめてから送る。送らないなら、仕様 JSON を手で書く道が残っている。
3. 仕様が埋まる。入力電圧の出典は「p.3 表2」、ゲインの出典は Excel のセルの位置、という形で、値ごとに出典が付いている。
4. スキャンの PDF は「読めなかったもの」の一覧に出る。インダクタンスはそのデータシートにしか書かれていないので、`null` のまま「不足」になっている。AI が、それらしい値で埋めることはない。
5. 高木さんはデータシートを見て、インダクタンスを入力する。出典は「手入力」になる。
6. 残りの値は、行から設計書の該当箇所を開いて見比べ、確認済みにしていく。
7. 不足が無くなり、実行できる。

決まっていない点: Excel に `100㎌` のような互換文字の単位があったときに、正規化して読むか、読めないものとして人に聞くか（D-037）。どちらにしても、黙って別の値にはしない。

通るユースケース: UC-10、11、02、03。

### SC-5 レビューする人と評価する人が、受け取った結果を確かめる

西村さんは設計審査のレビュー担当。三浦さんから、仕様 JSON と CSV（v0.2 からはレポートも）を受け取った。

2. 実行する。計算は決定的なので、同じ仕様 JSON からは同じ波形が出る。カーソルで読んだ値が、受け取った CSV の同じ時刻の値と、有効数字6桁で一致する。

5. 評価の岡田さんは、同じ仕様 JSON の負荷抵抗を書き換えたファイルをいくつか作り、コマンドラインでまとめて回して、CSV を実測の波形と重ねる。失敗した条件は、終了コードで分かる。
