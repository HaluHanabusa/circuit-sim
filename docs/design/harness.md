# 開発ハーネス

最終更新: 2026-11-15（W2: 手元の確認と、Windows での確認のゲート）

アプリ本体と同じ考え方で開発も回す。**判断はAI、手順と合否の扱いは決定的なコード。**
エージェントの呼び出しは決まった入口を通し、結果は構造化して保存し、ゲートの判定はスクリプトが行う。

## 1. 何をスクリプトが担うか

| 項目 | 担うもの | 理由 |
|---|---|---|
| 作業ツリーとブランチの用意 | `scripts/cycle.py start` | 手順の抜けを無くす |
| エージェントの起動 | `scripts/cycle.py run`（ヘッドレス） | 役割、仕様、道具、上限額を毎回同じ形で渡す |
| 自動確認 | `scripts/cycle.py check`（中身は `scripts/check.py`。ruff と pytest） | 通ったかどうかを記録に残す |
| ゲートの記録 | `.cycle/state/<ID>.json` | 誰が、何を見て、どう判定したかを残す |
| 統合の可否 | `scripts/cycle.py merge` | 条件を満たさない統合を機械的に拒む |
| 手元の確認 | `scripts/local_ci.py`（8章） | どのコミットが、どのOSで確認を通ったかを、GitHub上の自動テストに頼らずに記録する |
| Windows での確認の取り込み | `scripts/cycle.py record-ci` | 結果のファイルの中身（ツリーID、OS、合否）を確かめてから記録する |

エージェントが担うのは、実装、レビュー、独立検証、UX確認の中身だけ。

## 2. ゲートの決まり（スクリプトが強制する）

1. 必要なゲート（既定は implement、check、review、verify。画面を含む作業は ux も、Windows での確認が要る作業は windows も）がすべて合格していること。
   - 必要なゲートは仕様の見出しで決まる。見出しの書き間違い（知らない名前、`true` / `false` 以外の `needs_ux` と `needs_windows`、`needs_ux` と `gates` の食い違い）は、ゲートを減らす方向に読まずにエラーにする。
   - ゲートの記録がある作業単位では、見出し（owner、needs_ux、needs_windows、gates）を変えると `start` も `merge` も拒む。変えるなら `start --reset` で記録を消してやり直す。消したことは履歴と、統合のコミットメッセージに残る。
2. ゲートの結果は、そのとき見ていた内容（gitのツリーID）と一緒に記録する。**レビューや検証の後で内容が変わっていたら、そのゲートは無効**。やり直すまで統合できない。
   - 確認系のゲート（review、verify、ux）の対象は、確認を始める前の内容。ヘッドレスでは実行前のツリーを記録する。セッション内では `snapshot` で控えたツリーIDを `record --tree` で渡す（必須）。
   - `--tree` の値は、記録する時点でツリーIDに直す。`HEAD` やブランチ名のまま記録しない（後で動く名前は、決して「古く」ならないため）。
3. 例外として、検証担当が足す受け入れ試験（`tests/acceptance/`）と記録（`docs/verification/`）は、レビューの後に増えてよい。許すのは**ゲートの時点で無かったファイルの追加だけ**。既にあるファイルの書き換え、削除、名前の変更、他の場所からの移動は、例外の場所でも「変わった」と見なす。
4. 自動確認（check）は、統合する内容そのものに対して通っていること。
   - 取り込むのは作業ツリーの HEAD のコミット。そのツリーが check を通した内容と同じであることを、取り込みの直前に確かめる。`start` のときのブランチ名では取り込まない。HEAD がブランチから切り離された作業ツリーは拒む。
   - check の実行中に内容が変わったら、合格にしない（`error`）。
5. 実装した本人と検証した担当が同じなら統合できない。実装した担当は履歴の全体から集める（implement を別の名前で記録し直しても消えない）。
6. ヘッドレスの実行は、正常に終わり、構造化された結果に欠けも矛盾も無いときだけ合格にする。
   - 結果を得られなかった場合は `error`: 終了コードが 0 でない、時間切れ、`is_error` が真、必須の項目が無い、項目の形が違う。
   - 結果の中身が合格と矛盾する場合は `fail`: `verdict: pass` なのに critical の指摘がある、満たしていない基準（`pass: false`）がある。
7. main に取り込んだ後でもう一度自動確認を走らせ、失敗したら取り込みを取り消す。競合で取り込めない、確認スクリプトを起動できない、途中で止められた（Ctrl-C、終了の合図）場合も、本体を取り込み前の状態に戻す。
   - 後始末ができない止まり方（kill -9、電源断）に備えて、取り込みの間だけ控え（`.cycle/merge-pending.json`）を置く。控えが残っていたら、次の `merge` が最初に本体を取り込み前へ戻す。本体がその後で変わっていた場合（コミットが積まれた、手が入った、main にいない）は、何も動かさずに理由を表示して止まる。`status` は、控えが残っていることを知らせる。
8. 記録を失わない。記録の瞬間にロックを取り、状態を読み直してから書く。実行中に同じゲートの別の記録（または記録の消去）が入ったら、先に始めた実行の合格は採用しない（履歴には残す）。統合は1つずつ行う。
9. どのコマンドも、作業ツリーの索引（選んでステージした状態、競合の解決の途中）を変えない。内容のツリーIDは一時的な索引で計算する。
   - 同じ内容なら、どのOSでも同じツリーIDになる。一時的な索引は HEAD のコミットから組み直す（空からではない）。実行できる印を表せないファイルシステム（Windows の既定）では、git は索引に無いファイルを「実行できない普通のファイル」として足すので、空から組み直すと、印の付いたファイル（`scripts/*.py` など）を含む内容で、コミットのツリーとも Linux で求めたIDとも食い違う。
10. 仕様の見出しに `needs_windows: true` と書いた作業単位は、ゲート windows（その内容に対する、Windows での確認の合格）が要る。
    - 記録を作れるのは `record-ci` だけ。手元の確認（`scripts/local_ci.py`、8章）の結果のファイルを読んで取り込む。`record`（自己申告）と `run`（エージェントの判定）では記録できず、見出しの `gates:` にも書けない。
    - 取り込むのは、次のすべてを満たす結果だけ。それ以外は、記録を変えずにエラーで終わる: 形が正しい、`os.system` が `Windows`、作業ツリーのいまの内容に対する結果、合格と書かれているなら中身が合格と矛盾しない（確認の終了コードが 0、通過が1件以上、失敗とエラーが 0）。
    - 不合格（`fail`、`error`）の結果は、不合格として記録する（統合できない）。
    - 内容の突き合わせは、ほかの確認系のゲートと同じ（決まり2、3）。結果のツリーIDを記録し、結果の後で増えてよいのは、例外の場所への新しいファイルだけ。別のコミットの結果は、取り込みの時点でも、統合の時点でも拒む。

この決まりは `tests/test_harness.py` で確かめている。テストは、スクリプトの決まりを1つ外すと落ちるように書いてあり、スクリプトを1か所ずつ壊して全テストを流す方法で確かめている（件数と結果は5章）。決まりを足すときは、それを外すと落ちるテストを一緒に足す。

## 3. 使い方

仕様ファイル（`docs/plan/<ID>-<名前>.md`）の先頭に見出しを書く。

```
---
id: E1a
owner: solver-engineer
needs_ux: false
---
```

`gates: implement, check` のように書くと、必要なゲートを作業単位ごとに変えられる（文書だけの作業など）。

見出しに書けるのは `id`、`owner`、`needs_ux`、`needs_windows`、`gates` の5つだけ。`needs_ux` と `needs_windows` は `true` か `false`（注釈や引用符は付けない）。それ以外の行、知らない値、`needs_ux` と `gates` の食い違い（`needs_ux: true` なのに `gates` に ux が無い、など）はエラーになる。

コマンドは Windows、macOS、Linux で同じ（Linux / macOS では、先頭の `python` を省いて `scripts/cycle.py …` でもよい）。

```bash
python scripts/cycle.py start E1a            # 作業ツリー ../wt/E1a とブランチを用意
python scripts/cycle.py run E1a implement    # 担当（見出しの owner）をヘッドレスで起動
python scripts/cycle.py check E1a            # 自動確認（scripts/check.py）
python scripts/cycle.py run E1a review       # code-reviewer
python scripts/cycle.py run E1a verify       # verifier
python scripts/cycle.py status E1a           # ゲートの状況と、統合できない理由
# 作業ツリーでコミットしてから
python scripts/cycle.py merge E1a            # 条件を満たすときだけ main に取り込む（push は別）
```

セッション内でエージェントを動かしたときの記録:

```bash
TREE=$(python scripts/cycle.py snapshot E1a)     # 確認を始める前に、対象のツリーIDを控える
# （エージェントが確認する）
python scripts/cycle.py record E1a review --verdict pass --by <担当の名前> --tree "$TREE"
```

PowerShell では、1行目を `$TREE = python scripts/cycle.py snapshot E1a` と書く。

Windows での確認が要る作業単位（見出しに `needs_windows: true`）:

```bash
# 作業ツリーでコミットして、ブランチを push する。Windows のPCで（コマンド プロンプト）:
#   python scripts\local_ci.py --ref origin/<ブランチ>
# 書かれた結果のファイル（Windows のPCの .cycle/ci/ の下）を、ハーネスを動かす場所から読める所に置いて:
python scripts/cycle.py record-ci E1a --result <結果のファイル>
```

- `record` の `--tree` は review、verify、ux で必須。省けるのは implement だけ（いまの内容で記録する）。
- 検証担当とUX担当は、受け入れ試験と記録を**新しいファイルとして**足す。既にあるファイルを書き換えると、レビューと検証がやり直しになる（2回目の記録は `docs/verification/<ID>-2.md` のように別の名前で置く）。
- `merge` が取り込むのは、作業ツリーの HEAD のコミット。作業ツリーはブランチの上に置き、すべてコミットしておく。本体のチェックアウトは main で、未コミットの変更が無いこと。取り込むコミットが無い（変更の無いブランチ）ときは失敗する。
- `start` はやり直せる（記録は引き継ぐ）。ただし、ゲートの記録がある作業単位で見出しを変えた場合は `start E1a --reset` で記録を消してから、ゲートをやり直す。統合済みの作業単位は、`start` も `merge` もやり直せない。
- review と verify は並行で走らせてよい。同じゲートを同時に2つ走らせた場合、後から終わった合格は採用されないことがある（表示に従ってやり直す）。
- `claude` コマンドが無い環境では、`run` は記録を変えずにエラーで終わる。セッション内で動かして `record` で記録する。
- 自動確認は、`cycle.py` を動かしているのと同じ Python で `scripts/check.py` を実行する。`scripts/check.py` が無い作業ツリーは `error` になる（合格にはならない）。

## 4. エージェントの動かし方は2通り

| | ヘッドレス（`cycle.py run`） | セッション内（Claudeの画面からエージェントを起動） |
|---|---|---|
| 起動 | スクリプトが `claude -p --agent <役割> --output-format json --json-schema …` を実行 | オーケストレーターが役割ファイルを読ませて起動 |
| 結果の記録 | 自動（構造化された結果を確かめてから記録） | 始める前に `cycle.py snapshot` で対象を控え、終わったら `cycle.py record --tree <控えたID>` で記録 |
| 向いている場面 | 端末、定期実行、CI。人が見ていなくても同じ手順で動かしたいとき | 対話しながら進めるとき |
| 費用 | Claudeのプランでサインインしていれば、対話と同じサブスクの利用枠から引かれる（別枠にはならない）。APIキーで実行した場合はAPIの料金になる。暴走に備えて、1回の上限額を `--budget` で指定する（既定は5ドル相当） | サブスクの利用枠 |
| 注意 | CLIにログイン済みの環境が要る | 返信を終えると実行中のエージェントは止まる。完了を見届けてから返信する |

どちらで動かしても、ゲートの決まり（2章）は同じスクリプトが強制する。

## 5. 確認できていること、いないこと

- 確認済み:
  - ゲートの決まり（`tests/test_harness.py`）。W1 までは、Linux（Python 3.11〜3.13）と Windows（3.11、3.13）の GitHub上の自動テストで、push のたびに流していた。W2 からは、手元の確認（8章）で流す。GitHub上の自動テストは、手で起動したときだけ走る（7章）。
  - テストの実効性（2章の末尾の方法）。H1 の時点では、139通りの壊し方のすべてでテストが落ちた。W1 では、Windows でしか実行されない分岐（ロック、Ctrl-Break、打ち切りで止める範囲、置き換えの待ち、パスの区切りなど）を9通り壊して、Windows の実物（GitHub上の自動テスト）で流した。8通りでテストが落ちた。残る1通りは、壊しても動作が変わらない余分な分岐だったので、分岐そのものを消した。
  - ヘッドレス起動のコマンドの形（`--dry-run`）と、結果の取り込み（偽のCLIを使ったテスト）。Windows では、偽のCLIを npm 版と同じ `claude.cmd` の形で置き、指示（日本語）と結果の形の指定（JSON）が崩れずに届くことを確かめている。
- 途中のもの: 機械的に1か所ずつ壊す確認（W1）。
  - W1 で変えた後のスクリプトから機械的に作った壊し方は 1165 通り。実行したのは 600 通りで、その中に生き残りがある（実装の担当の報告では 38。一覧はリポジトリに残っていない）。残りの 565 通りと、`scripts/doctor.py` の壊し方は、実行していない。「生き残りが無い」とは、まだ言えない。残りは H2 で消化する。
  - 独立検証が手で作った 78 通り（`docs/verification/W1-verifier.md` の「壊す確認」）では、生き残りが 10、試験が止まらなくなるものが 1 あった。それぞれに試験を足した。足した後に、今回の変更と上の生き残りを手で壊し直した 54 通りを流した（Linux。道具の試験 3 ファイル）。53 通りで試験が落ち、止まらなくなるものは無かった。残る 1 通りは、動作が変わらない書き換え（`doctor.py` で、結果のオブジェクトが無いときの扱いを別の書き方にしたもの）。Windows でしか通らない分岐（PATHEXT の拡張子、PATH に書かれていない実行した場所）を壊す確認は、していない。
  - Windows でしか違いが出ない壊し方のうち、状態ファイルの改行と、`claude` の出力を読む文字コードは、Linux でも落ちる試験にした（改行は、Windows と同じ書き込みを模擬する。文字コードは、既定が UTF-8 でない Python を起動する）。記録するパスの区切りと、置き換えを待つ秒数は、Windows の自動テストでだけ落ちる。
- 未確認: 本物のCLIでのヘッドレス実行。クラウドの作業環境ではCLIの認証が通らず、試せなかった。結果の読み方（`is_error`、`subtype`、`structured_output`、`session_id`）も、本物の出力とは突き合わせていない。形が違えば `error` になる（合格にはならない）。
  - 確かめ方: CLIにサインイン済みのPCで `python scripts/doctor.py --headless` を実行する（7章）。本物の `claude -p` を、`cycle.py run` と同じ組み立てで1回だけ実行し、出力の形を `.cycle/doctor-result.json` に記録する。`headless.unexpected` が空なら、前提どおり。空でなければ、その記録（形と真偽だけで、本文は入っていない）をもとに `cycle.py` の読み方を直す。
- スクリプトでは守れないこと:
  - 担当の名前（`--by`）と、セッション内の合否（`record --verdict`）は自己申告。記録ファイル（`.cycle/state/`）は手で書き換えられる。
  - 手元の確認の結果のファイル（`.cycle/ci/`）も、手で書き換えられる。`record-ci` が確かめるのは、ファイルに書かれた中身（形、OS、ツリーID、合否と件数の矛盾）で、本当に Windows で実行されたかどうかは確かめられない。結果のファイルは、実行したPCから、そのまま渡す。
  - Windows での結果の後で、例外の場所に足された受け入れ試験は、Windows では流れていない（Linux の check は通っている）。気になる場合は、足した後の内容で、もう一度 Windows で確かめて取り込む。
  - 手元の確認は、`local_ci.py` を動かした Python に入っている依存ライブラリで走る（まっさらな環境は作らない）。結果には、OS と Python の版は入るが、ライブラリの版は入らない。
  - main が先に進んでいると、取り込んだ結果は確認した内容と同じにならない。この差を見るのは、取り込んだ後の自動確認（決まり7）だけ。
  - 例外の場所に足したファイルはレビューを通らない。`scripts/check.py` 自体の書き換えを止めるのはレビュー。
  - 取り込みの途中でプロセスが強制終了された場合（kill -9、電源断。道具の時間切れで止められた場合を含む）、確認の済んでいない取り込みコミットは、次に `merge` を実行するまで main に残る。`merge` が正常に終わらなかったら、push の前に `status` で「注意」が出ていないことを確かめる。
  - Linux / macOS では、打ち切り（`--timeout`）で止めるのは、起動した `claude` だけ。`claude` が残した子プロセスは動き続ける（`run` は待たずに戻り、`error` を記録する）。
- 未確認（Windows で、実行した場所のファイルが先に動く経路。W1 で塞いだのは `claude` の見つけ方だけ）:
  - npm 版の `claude.cmd` は、中で `node` を名前だけで呼ぶ。cmd.exe は、実行した場所（`run` では作業ツリー）を PATH より先に探すので、作業ツリーの直下に `node.cmd` や `node.exe` があれば、そちらが動くはず。
  - `cycle.py` は git を名前だけで起動する。Windows は、実行した場所の `git.exe` を PATH より先に探すはず。
  - どちらも、Windows では試していない。塞ぐなら、起動するプロセスの環境変数に `NoDefaultCurrentDirectoryInExePath` を足す、git を `claude` と同じ探し方で絶対パスにする、などを H2 で検討する。

## 6. 記録の場所

- `.cycle/state/<ID>.json`: ゲートの状態と履歴（gitには入れない。統合時に、ゲートの結果、取り込んだコミットとツリーID、記録を消した回数をコミットメッセージに書く）。履歴には、採用しなかった結果（`adopted: false`）と、記録の消去（`event: reset`）も残る
- `.cycle/state/<ID>.lock`、`.cycle/merge.lock`: 記録と統合のロック（中身は空）
- `.cycle/merge-pending.json`: 取り込みの間だけある控え（作業単位、取り込み前のコミット、取り込むコミット）。残っていたら、前回の `merge` が途中で止まっている
- `.cycle/runs/`: ヘッドレス実行の生の出力、自動確認のログ（取り込んだ後の確認は `<ID>-merge-check-*.log`）、`record-ci` で取り込んだ結果の写し（`<ID>-windows-*.json`）
- `.cycle/ci/`: 手元の確認（`scripts/local_ci.py`）の結果。1回の実行につき1つのファイル（8章）
- `.cycle/doctor-result.json`: 環境の確認（`scripts/doctor.py`）の結果。確かめた内容（コミットID、ツリーID、ブランチ、未コミットの変更の有無）も入る

## 7. OSの違いと、環境の確認

対象は Windows、macOS、Linux。ゲートの決まり（2章）は、どのOSでも同じコードが強制する。

### OSで違う箇所

`scripts/cycle.py` の「OSの違い」の節にまとめてある。ほかの場所では、OSを見て分岐しない。

| 項目 | Linux / macOS | Windows |
|---|---|---|
| ロック | `fcntl.flock` | `msvcrt.locking`（ロックのファイルの先頭1バイト。取れるまで待つ） |
| 終了の合図（統合を取り消してから終わる） | Ctrl-C、SIGTERM、SIGHUP | Ctrl-C、Ctrl-Break |
| 後始末ができない止まり方（決まり7の控えで、次の `merge` が戻す） | kill -9、電源断 | タスクの強制終了（`taskkill /F`）、端末を閉じる、電源断 |
| `claude` として起動するファイル | PATH の上の `claude` | PATH の上の `claude.exe`、`claude.cmd`、`claude.bat`（環境変数 PATHEXT の拡張子）。拡張子の無い同名のファイル（シェル用）は使わない |
| `claude.cmd` を通る起動 | — | cmd.exe を通るので、引数に `%` `^` `&` `\|` `<` `>` `!` `(` `)` と改行があれば、起動せずにエラーにする（崩れた指示を渡さない。`!` は遅延展開、`(` `)` は引数をかっこの中に置く起動ファイルへの備え） |
| 時間切れ、中断で止める範囲 | 起動したプロセス | 起動したプロセスと、その先のプロセス（`taskkill /T`）。`claude.cmd` の先の本体まで止める |
| 状態ファイルの置き換えと読み取り | そのまま | 他のプロセスが開いている間は一時的に拒まれるので、5秒まで待ってやり直す。それでも駄目ならエラーで終わる（記録は変えない） |
| 手元の確認で取り出した場所の後始末 | そのまま消す | 中のファイルが使われている間は消せないので、同じ5秒まで待ってやり直す。git が作業ツリーを消せなかったときは、フォルダを消してから、登録を外し直す。それでも残ったら、場所を表示する |

どのOSでも共通にしていること:

- ファイルは UTF-8 で読み書きする。状態ファイルと結果のファイルの改行は LF。記録に残すパス（仕様、ログ）は `/` 区切り。
- 内容のツリーIDは、同じ内容なら同じ（決まり9）。実行できる印とリンクは、HEAD のコミットのとおりに扱う。
- git と `claude` の出力は UTF-8 として読む。自動確認（`scripts/check.py`）は `cycle.py` と同じ Python で起動し、出力を UTF-8 で受け取る。
- `claude` は、PATH の項目のうち絶対パスで書かれたものを、書かれた順に探す。次の場所にあるものは使わない: 実行した場所（カレント）、作業ツリーの中、本体の中。空の項目と相対パスの項目も使わない。確認を受けていないファイル（作業ツリーに置かれた `claude.cmd`、無視の対象の `node_modules` の中のものなど）が、レビューや検証の合格を返せないようにするため。Windows の端末は PATH より先に実行した場所を探すが、それには合わせない。`doctor.py` が git と `claude` を探すときも同じ（本体の中のものは、版を聞くための起動もしない）。
- 打ち切りと中断で `claude` を止めた後は、出力の終わりを待たずに戻る（`claude` が残した子プロセスが出力の口を持ったままでも、`--timeout` が効く）。
- `claude` には、呼び出し元の標準入力を渡さない（入力を待って止まり続けないように）。
- 画面に出せない文字（UTF-8 でない端末での日本語や記号）は `?` に置き換えて表示する。例外では止まらない。
- リポジトリの改行は `.gitattributes` で LF に固定している。

### 自動テスト

`.github/workflows/ci.yml`。**手で起動したときだけ走る**（GitHub の画面の「Run workflow」。push では走らない。D-031）。ふだんの確認は、手元の確認（8章）で行う。GitHub上の自動テストは、手元に無い組み合わせ（別の版の Python など）を確かめたいときの補助で、無料枠を使うので、起動する前にPOに確かめる。

- Linux（Python 3.11、3.12、3.13）と Windows（3.11、3.13）。
- 中身は、`python scripts/check.py`（ruff と pytest）、`python scripts/doctor.py --no-check`、cp932 の端末（`PYTHONIOENCODING=cp932`）での `python -m circuit_sim` の実行2件。
- 合否は `scripts/check.py` の終了コードで直接決まる（`doctor.py` の終了コードには懸けない）。`doctor.py` は別のステップで動かし、確認（check）は重ねて実行しない。結果のファイルに問題（`problems`）が無いことも確かめる。`doctor.py` が確認を実行して結果を記録する経路は、試験（`tests/test_dev_tools.py`）が Linux と Windows の両方で確かめる。
- 自動テストに渡す権限は、リポジトリの読み取りだけ（`permissions: contents: read`）。
- 試験の中から、このリポジトリの試験がもう一度実行された場合（確認スクリプトを起動する試験で、起動する場所の指定が壊れたとき）は、すぐに止める（`tests/conftest.py`）。
- Windows の実行は、文字コードの設定を足していない素の状態（既定の文字コードは UTF-8 ではない）で流す。
- ハーネスの試験は Windows でも同じものが走る。スキップするのは、Windows に無い機能そのものを試す3件（他のプロセスへ SIGINT、SIGTERM、SIGHUP を送って `merge` を止める試験）だけ。その代わりに、Windows にだけある挙動を試す2件（Ctrl-Break で止める試験、他のプログラムが開いたままの状態ファイルを置き換える試験）が Windows でだけ走る（Linux では、この2件をスキップする）。Ctrl-C で止めた場合の取り消しは、同じプロセスの中で起こす試験が、どのOSでも確かめる。スキップした試験と理由は、実行ログの最後に一覧で出る（`pytest -rs`）。

### 環境の確認（`scripts/doctor.py`）

自分のPCで、開発の道具が動く環境かどうかを確かめる。

```bash
python scripts/doctor.py               # OS、Python、文字コード、git、claude の有無と版、scripts/check.py の結果
python scripts/doctor.py --no-check    # scripts/check.py（数分かかる）を省く
python scripts/doctor.py --headless    # 加えて、本物の claude -p を1回だけ実行して、出力の形を確かめる
```

- 結果は画面と `.cycle/doctor-result.json` に出る。終了コードは、必要なもの（Python 3.11 以上、git、`scripts/check.py` の合格、頼まれたヘッドレスの確認）に問題が無ければ 0。`claude` が無いことは、それだけでは問題にしない（セッション内で動かせる）。
- `--headless` は、付けたときだけ実行する。Claudeの利用枠を少し使うので、実行の前に、何をするか（役割、道具、上限額、指示の全文、実行するコマンド）を表示する。コマンドは `cycle.py run` と同じ関数で組み立てる（`--agent`、`--output-format json`、`--json-schema`、`--permission-mode`、`--max-budget-usd`、`--allowedTools`）。指示は「何も読まず、決まった形の結果だけを返す」という最小のもの。
- APIキーの環境変数（`ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`）が設定されていると、利用枠ではなくAPIの料金になる。その場合は実行せずに知らせる（`--allow-api-billing` を付けたときだけ実行する）。
- 記録するのは形と真偽だけ: 終了コード、出力の形（JSON のオブジェクトか、一覧か、行ごとか、JSON でないか）、項目の名前、`is_error`・`subtype`・`structured_output`・`session_id`・`result` などの有無と型、ハーネスが同じ出力を読んだときの判定、前提と違っていた点の一覧（`unexpected`）。値まで記録するのは、真偽、数（費用の概算など）、種類を表す英小文字の語（`success` など）だけ。
  - 項目の名前は、あらかじめ決めた一覧（ハーネスが読む項目と、CLI の出力にある決まった名前）にあるものだけを残す。それ以外は、個数だけを記録する（`other_keys`）。
  - `structured_output` が無い（オブジェクトでない）ときは、`result` の文字列が JSON として読めるか、決まった形に合うかを記録する（`result_as_json`。中身は記録しない）。本物の CLI が結果を `result` の側に返していたら、`cycle.py` の読み方を直す。
- 確かめた内容（`content`）: コミットID、ツリーID（`cycle.py` と同じ求め方。未コミットの変更を含む）、ブランチ、未コミットの変更の有無。gitの作業ツリーの最上位でない場所や、コミットがまだ無い場所では、どれも `null`。
- 記録しないもの: 応答の本文（`result`、`summary`、基準や指摘の文面）、セッションのID、エラーの文面、環境変数の中身、コマンドの置き場所。エラーの文面からは、「こちらが渡したオプションのうち、CLIが知らないと言ったもの」と「サインインや認証に触れているか」だけを取り出す。くわしい原因は、表示されたコマンドを自分の端末で実行して確かめる。

## 8. 手元の確認（`scripts/local_ci.py`）

GitHub上の自動テストに頼らず、手元のPCで「どのコミットが、どのOSで、確認を通ったか」を確かめて、記録に残す（D-031）。
Windows での確認は、Windows のPCでこれを実行して行う。

### 使い方

```bash
python scripts/local_ci.py                  # リモート（origin）の最新を取得し、origin/main を取り出して確認する
python scripts/local_ci.py --ref origin/W2  # 確かめるコミットを指定する（ブランチ、タグ、コミットID）
python scripts/local_ci.py --no-fetch       # リモートから取得しない（手元にあるコミットを確かめる）
python scripts/local_ci.py --current        # 取り出さずに、いまの作業フォルダの内容（未コミットの変更を含む）で確認する
python scripts/local_ci.py --force          # 同じ内容の結果が既にあっても、やり直す
```

- 終了コード: 0 = 合格、1 = 不合格（確認が失敗した、結果を得られなかった）、2 = 確認を始められなかった（取得できない、コミットを読めない、結果を書けない）。
- 確認の出力（ruff と pytest）は、そのまま画面に流れる。どこにも記録しない。
- 同じ内容（コミットとツリー）を、同じ環境（OS、Python の版）で、同じやり方（取り出したか、作業フォルダか）で確かめた結果が既にあれば、実行せずにそれを示す。終了コードは、その結果の合否に従う。複数あれば、最も新しいもの。結果を得られなかった実行（`error`）の記録、読めないファイル、形の違うファイルは、結果として扱わない。
- 取得（`git fetch origin`）は、端末での入力を求めさせず、300秒で打ち切る。取得できなければ、古い内容を「最新」として確かめないよう、何も実行せずに終わる。git の出力は表示しない（リモートのURLに、認証情報が入っていることがある）。

### 取り出して実行する

- 取り出すのは、git の作業ツリー（`git worktree add --detach`）。あるのは、コミットにある内容だけ。作業中のフォルダの未コミットの変更、新しいファイル、無視されているファイル（`.venv` など）は無い。作業中のフォルダには触らない。
- 取り出す場所は、**リポジトリの外**（OSの一時フォルダの `circuit-sim-ci-…/checkout`）。`.cycle/` の下にしなかった理由:
  - 作業中のフォルダの下に置かなければ、道具（ruff、pytest、git）が設定や無視の指定を探して上の階層をたどっても、作業中のフォルダには行き着かない。探し方は道具ごとに違い、版でも変わるので、たどられても困らない場所に置く。
  - 試験が一時リポジトリと作業ツリーを作るのと同じ場所で、W1 の試験が Windows の実機で通っている。パスの長さも、リポジトリの置き場所に左右されない。
  - リポジトリのフォルダが同期の対象になっている場合（OneDrive など）、取り出した内容まで同期され、後始末で消せなくなるおそれがある（確かめてはいない）。
  - 欠点: 後始末ができない止まり方をすると、リポジトリの外に残るので、気づきにくい（下の「後始末」）。
- 取り出した直後に、内容のツリーID（`cycle.py` の `tree_id` と同じ求め方）が、コミットのツリーと同じであることを確かめる。違えば、確認を実行せずに `error` にする。
- 実行するのは、取り出した場所の `scripts/check.py`。`local_ci.py` を動かしたのと同じ Python で起動する。`circuit_sim` は、取り出した場所のものが読み込まれる（pytest の設定 `pythonpath` と、実行する場所）。
- 件数と、失敗した試験の名前は、pytest に試験ごとの結果のファイル（JUnit の形）を書かせて読む。オプションは環境変数 `PYTEST_ADDOPTS` で渡す（`scripts/check.py` は変えないので、どのコミットでも同じに動く）。ファイルは、取り出した内容の外に置き、終わったら消す。読み出すのは、件数と名前だけ。
- 後始末: 終わったら、合否にも例外にも関係なく（Ctrl-C、終了の合図でも）、取り出した場所を消し、git の作業ツリーの登録を外す。消せなかったときは、場所を表示する（合否は変えない）。後始末ができない止まり方（強制終了、電源断）では、一時フォルダに `circuit-sim-ci-…` が残る。消してよい（登録は `git worktree prune` で外れる）。
- 試験の入れ子を止める仕組み（7章）とは干渉しない。目印の環境変数を消さずに引き継ぐので、試験の中から、このリポジトリを対象に `local_ci.py` が実行されても、取り出した先の pytest は、すぐに止まる。

### 合否

合格（`pass`）にするのは、次のすべてを満たすときだけ。迷う場合は、不合格の側に倒す。

- `scripts/check.py` の終了コードが 0
- 確かめた内容が、実行の前も後も、対象のツリーと同じ
- 試験ごとの結果を読めて、通過が1件以上、失敗とエラーが 0

| `verdict` | `reason` | 意味 |
|---|---|---|
| pass | ok | 確認が通った |
| fail | tests_failed | 失敗した試験がある（名前は `failed`） |
| fail | check_failed | 確認が失敗したが、試験の失敗は報告されていない（ruff の指摘、試験を始められなかった、など） |
| error | content_mismatch | 確認を始める時点の内容が、対象のツリーと違う（違うファイルは `changed`）。確認は実行していない |
| error | content_changed | 確認の実行中に、内容が変わった（違うファイルは `changed`） |
| error | no_test_results | 終了コードは 0 だが、試験ごとの結果を読めない |
| error | test_results_disagree | 終了コードは 0 だが、試験ごとの結果が合格と合わない（失敗やエラーがある、通過が無い） |
| error | timeout | 時間内（`--timeout`、既定は 3600 秒）に終わらなかった。確認のプロセスは止める |

### 結果のファイル

`.cycle/ci/<時刻>-<OS>-<コミットの先頭10桁>.json`。1回の実行につき1つ（UTF-8、改行は LF）。

| 項目 | 中身 |
|---|---|
| `schema`、`kind`、`at` | 形の版（1）、種類（`local-ci`）、書いた時刻（UTC） |
| `mode`、`ref` | 取り出して確かめた（`checkout`）か、作業フォルダで確かめた（`current`）か。指定された名前 |
| `commit`、`tree`、`branch`、`dirty` | コミットID、内容のツリーID、ブランチ（名前で指定されていれば）、未コミットの変更の有無 |
| `os`、`python`、`encoding` | OS（種類、版、機種）、Python の版、文字コード（既定、画面、ファイル名） |
| `check` | 確認スクリプト、終了コード、所要時間（秒）、時間切れか |
| `tests` | 件数（`total`、`passed`、`failed`、`errors`、`skipped`）。読めなければ `null`。`skipped` には、失敗を見込んだ試験（xfail）を含む |
| `failed` | 失敗した試験と、エラーになった試験の名前（pytest のノードID） |
| `changed` | 内容が違っていたファイルの名前（先頭の20個まで） |
| `verdict`、`reason` | 合否と理由（上の表） |

入れないもの: 認証情報、環境変数の中身、試験の出力の本文、失敗の文面、PCの名前、フォルダの場所。

### ハーネスとのつなぎ（`needs_windows`）

1. 仕様の見出しに `needs_windows: true` と書く（`start` の前。記録の後で変えるなら `start --reset`）。
2. 実装、check、レビュー、検証を済ませ、作業ツリーでコミットして、ブランチを push する。
3. Windows のPCで（コマンド プロンプト）: `python scripts\local_ci.py --ref origin/<ブランチ>`
4. 結果のファイル（Windows のPCの `.cycle\ci\` の下）を、ハーネスを動かす場所から読める所に置き、`python scripts/cycle.py record-ci <ID> --result <ファイル>` で取り込む。
5. `python scripts/cycle.py status <ID>` で確かめ、`merge` する。

結果の後で内容を変えたら（例外の場所への新しいファイルを除く）、3 からやり直す。

### 定期的に回したい場合（Windows のタスク スケジューラ）

登録するかどうかは、POが決める（スクリプトは登録しない）。**この手順は、実機では確かめていない。**

1. リポジトリの外に、起動用のファイルを作る。たとえば `%USERPROFILE%\circuit-sim-ci.cmd`:

   ```bat
   @echo off
   cd /d "C:\（リポジトリの場所）\circuit-sim"
   python scripts\local_ci.py
   ```

2. コマンド プロンプトで登録する（毎日 12:30 に実行する例）:

   ```bat
   schtasks /Create /TN "circuit-sim-local-ci" /SC DAILY /ST 12:30 /TR "%USERPROFILE%\circuit-sim-ci.cmd"
   ```

   画面から登録する場合は、タスク スケジューラの「基本タスクの作成」で、操作に「プログラムの開始」、プログラムに上の `.cmd` を指定する。

3. 止めるとき: `schtasks /Delete /TN "circuit-sim-local-ci"`

- 既定の「ユーザーがログオンしているときのみ実行する」のままにする（`git fetch` が、そのユーザーの認証情報を使うため）。
- `origin/main` が進んでいなければ、既にある結果を示すだけで終わる（確認は走らない）。進んでいれば、約4〜5分かかる。
- 結果は `.cycle\ci\` に増えていく。古いものは消してよい。
- `python` が見つからない場合は、起動用のファイルの `python` を、`py -3` か、Python の実体の場所に変える。
