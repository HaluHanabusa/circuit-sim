# 開発ハーネス

最終更新: 2026-11-14

アプリ本体と同じ考え方で開発も回す。**判断はAI、手順と合否の扱いは決定的なコード。**
エージェントの呼び出しは決まった入口を通し、結果は構造化して保存し、ゲートの判定はスクリプトが行う。

## 1. 何をスクリプトが担うか

| 項目 | 担うもの | 理由 |
|---|---|---|
| 作業ツリーとブランチの用意 | `scripts/cycle.py start` | 手順の抜けを無くす |
| エージェントの起動 | `scripts/cycle.py run`（ヘッドレス） | 役割、仕様、道具、上限額を毎回同じ形で渡す |
| 自動確認 | `scripts/cycle.py check`（中身は `scripts/check.sh`） | 通ったかどうかを記録に残す |
| ゲートの記録 | `.cycle/state/<ID>.json` | 誰が、何を見て、どう判定したかを残す |
| 統合の可否 | `scripts/cycle.py merge` | 条件を満たさない統合を機械的に拒む |

エージェントが担うのは、実装、レビュー、独立検証、UX確認の中身だけ。

## 2. ゲートの決まり（スクリプトが強制する）

1. 必要なゲート（既定は implement、check、review、verify。画面を含む作業は ux も）がすべて合格していること。
2. ゲートの結果は、そのとき見ていた内容（gitのツリーID）と一緒に記録する。**レビューや検証の後で製品のコードが変わっていたら、そのゲートは無効**。やり直すまで統合できない。
3. 例外として、検証担当が足す受け入れ試験（`tests/acceptance/`）と記録（`docs/verification/`）は、レビューの後に増えてよい。
4. 自動確認（check）は、統合する内容そのものに対して通っていること。
5. 実装した本人と検証した担当が同じなら統合できない。
6. ヘッドレスの実行が構造化された結果を返さなかったら、合格として扱わない（`error`）。
7. main に取り込んだ後でもう一度自動確認を走らせ、失敗したら取り込みを取り消す。

この決まりは `tests/test_harness.py` で確かめている。

## 3. 使い方

仕様ファイル（`docs/plan/<ID>-<名前>.md`）の先頭に見出しを書く。

```
---
id: E1a
owner: solver-engineer
needs_ux: false
---
```

`gates: implement, check` のように書くと、必要なゲートを作業単位ごとに変えられる（文書だけの作業など）。

```bash
scripts/cycle.py start E1a            # 作業ツリー ../wt/E1a とブランチを用意
scripts/cycle.py run E1a implement    # 担当（見出しの owner）をヘッドレスで起動
scripts/cycle.py check E1a            # 自動確認
scripts/cycle.py run E1a review       # code-reviewer
scripts/cycle.py run E1a verify       # verifier
scripts/cycle.py status E1a           # ゲートの状況と、統合できない理由
# 作業ツリーでコミットしてから
scripts/cycle.py merge E1a            # 条件を満たすときだけ main に取り込む（push は別）
```

## 4. エージェントの動かし方は2通り

| | ヘッドレス（`cycle.py run`） | セッション内（Claudeの画面からエージェントを起動） |
|---|---|---|
| 起動 | スクリプトが `claude -p --agent <役割> --output-format json --json-schema …` を実行 | オーケストレーターが役割ファイルを読ませて起動 |
| 結果の記録 | 自動（構造化された結果をそのまま記録） | `cycle.py snapshot` で対象を控え、終わったら `cycle.py record` で記録 |
| 向いている場面 | 端末、定期実行、CI。人が見ていなくても同じ手順で動かしたいとき | 対話しながら進めるとき |
| 費用 | 月次のAgent SDKクレジットから引かれる。1回の上限額を `--budget` で指定（既定5ドル） | 通常の利用枠 |
| 注意 | CLIにログイン済みの環境が要る | 返信を終えると実行中のエージェントは止まる。完了を見届けてから返信する |

どちらで動かしても、ゲートの決まり（2章）は同じスクリプトが強制する。

## 5. 確認できていること、いないこと

- 確認済み: ゲートの決まり（テスト11件）。ヘッドレス起動のコマンドの形（`--dry-run`）と、結果の取り込み（偽のCLIを使ったテスト）。
- 未確認: 本物のCLIでのヘッドレス実行。クラウドの作業環境ではCLIの認証が通らず、試せなかった。POのPCなど、CLIにログイン済みの環境で `scripts/cycle.py run <ID> review --dry-run` の表示を確かめ、次に小さな作業で実行して確認する必要がある。

## 6. 記録の場所

- `.cycle/state/<ID>.json`: ゲートの状態と履歴（gitには入れない。統合時にゲートの結果をコミットメッセージに書く）
- `.cycle/runs/`: ヘッドレス実行の生の出力、自動確認のログ
