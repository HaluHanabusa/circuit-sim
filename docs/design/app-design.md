# アプリ設計（v0.1）

最終更新: 2026-11-14 ／ 責任者: ux-designer

この文書は、全リリースに共通の骨格と原則を書く。詳細は次の文書にある。

- 画面ごとの仕様: `screens-v0.1.md`（リリースごとに `screens-*.md` を足す）
- 色・文字・部品の基準: `design-system.md`

## 1. 誰の、どんな用事か

**利用者**: パワーエレクトロニクスやモーター制御の設計者。設計書（仕様と回路定数）は手元にあるが、シミュレーションモデルを組み、ゲインを調整し、結果を資料にまとめる作業に時間を取られている。回路シミュレータとオシロスコープに慣れていて、数値の正しさと出どころに厳しい。

**済ませたい用事**:

1. 設計書の内容で回路がどう動くか、すぐ見たい。
2. 目標（オーバーシュート、整定時間、安定余裕）を満たすゲインが欲しい。満たせないなら、何がどれだけ足りないか知りたい。
3. 結果を、根拠つきで人に渡せる形で残したい。

## 2. 中心になる流れ

```
① 取り込む ─► ② 確かめる ─► ③ 動かす ─► ④ 決める ─► ⑤ 残す
 設計書を     値・出どころ・   計算して     目標値から    レポートと
 開く         不足を確認       波形を見る   ゲインを出す  仕様の保存
```

- どの段階からでも始められる。v0.1 は ② と ③（仕様JSONを開き、値を確かめて直し、動かす）。① は v0.3、④ と ⑤ は v0.2 から。
- 前の段階に戻って値を直すと、後ろの結果は「古い」と表示され、再計算を促す。古い結果は、どの値で計算したものかと、いまの値との違いを添えて見せる。

## 3. 画面の構成

1つの作業画面で完結させる。段階ごとにページを切り替えない。

```
┌───────────────────────────────────────────────────────────────────────────┐
│ アプリ名  開いている仕様  開く・保存  （段階の表示）  実行と状態  言語 テーマ │
├──────────────┬────────────────────────────────┬───────────────────────────┤
│ 仕様         │ 回路図（テンプレートの固定図）  │ 目標値と結果（v0.2 から） │
│  値  単位    │                                │  目標 / 実測              │
│  出どころ    ├────────────────────────────────┤  達成 / 未達              │
│  不足の表示  │ スコープ（波形）                │  ゲイン                   │
│              │                                │  安定余裕                 │
├──────────────┴────────────────────────────────┴───────────────────────────┤
│ お知らせ（不足、注意、エラーと直し方）                                     │
└───────────────────────────────────────────────────────────────────────────┘
```

| 領域 | 役割 | 入るリリース |
|---|---|---|
| ヘッダー | 開いている仕様、開く・保存、実行と進み具合、言語とテーマ。段階の表示（①〜⑤の現在地）は v0.2 から | v0.1 |
| 仕様パネル | 値、単位、出どころを一覧し、その場で直す | v0.1（値・単位・出どころの表示と編集）、v0.3（出どころを設計書の位置につなぐ、確認済みの印） |
| 回路図 | テンプレートごとの固定図に値を重ねて表示。素子を選ぶと仕様パネルの行が強調される。測定点から波形の表示を切り替える | v0.1 |
| スコープ | 波形の表示、拡大縮小、カーソル、重ね書き、前回との比較、CSV書き出し | v0.1 |
| 目標値と結果 | 目標の入力、実測値、達成状況、ゲイン、安定余裕 | v0.2 |
| お知らせ | 不足、注意、エラー。必ず「どう直すか」を添える | v0.1 |
| 取り込み | 設計書を開き、読み取り結果と読めなかった箇所を見る | v0.3 |
| レポート | 仕様、波形、ゲイン、達成状況、根拠を1つにまとめて書き出す | v0.2 |

**まだ使えないものを先に置かない。** そのリリースで使えない領域や段階は、薄く表示したり「準備中」と書いたりせず、画面に出さない。場所だけを骨格として空けておく（どこに入るかは `screens-v0.1.md` 13章）。段階の表示は、使える段階が2つ以上になってから出す。

## 4. 設計の原則

洗練の基準。画面仕様とレビューはこれに照らす。迷ったら「間違いに気づける ＞ 速く用事が済む ＞ 見た目の整い」の順で決める。

1. **数値には必ず単位。** 工学表記（47 µH、100 kHz）で読めて、同じ表記で入力できる。入力をどう読んだかを、その場で見せる（m と M の取り違えに、打った瞬間に気づける）。ファイルに書かれた単位は必ず読み、換算したらそう知らせる。丸めて表示するときは、丸めたと分かるようにする。
2. **すべての値に出どころ。** 設計書の位置、手入力、既定値、自動のどれかを必ず示す。書かれていないなら「記載なし」と示す。
3. **推測で埋めない。** 足りない値は足りないと見せ、次に何をすればよいかを示す。
4. **達成と未達を隠さない。** 色だけに頼らず、言葉と数値で示す。未達は「どの目標が、どれだけ」まで書く。
5. **待たせない。** 操作への反応は0.1秒以内。計算は進み具合を見せ、いつでも止められる。計算中も画面は使える。始められない計算（値の不足、大きすぎる計算）は、実行する前に、理由と直す場所を示す。
6. **戻せる、比べられる。** 値を変える前の結果を残し、波形を重ねて比べられる。いま見ている結果が、どの値で計算したものかを常に示す。
7. **波形が主役。** スコープは最も広い場所を取り、拡大縮小とカーソルが滑らかに動く。読み取る数値は、画面用に間引いた点ではなく、計算結果の値そのもの。波形をそのまま信じてよいかに関わること（古い結果、計算からの注意）は、波形のすぐそばに出す。
8. **設計者の言葉を使う。** オーバーシュート、整定時間、位相余裕。ソフトウェア都合の言葉を出さない。
9. **エラーは原因と直し方を対で。** 「回路が解けません」で終わらせない。プログラムの内部の文は主文に出さない。
10. **慣習に従う。** 既存の回路シミュレータとオシロスコープの操作に合わせ、独自の操作を発明しない。主要な操作はキーボードでもできる。
11. **色に意味を持たせるのは波形と状態だけ。** 枠や操作の部品は無彩色で作る。状態は記号と言葉を必ず添え、波形は名前と線の種類でも見分けられるようにする。

## 5. 品質の基準

| 項目 | 基準 |
|---|---|
| はじめての利用 | インストール後、同梱のサンプルで波形を見るまで3分以内。説明を読まずにたどり着ける |
| スコープの反応 | 2000万点の信号を2本表示した状態で、拡大・縮小・移動の操作から、間引き直した波形に置き換わるまで0.1秒以内（同じ操作を30回以上くり返した95パーセンタイル） |
| 計算中 | 進み具合が見え、中断できる。中断しても画面が固まらない。中断から1秒以内に操作できる状態に戻る |
| 状態の網羅 | どの画面にも、読み込み中・空・正常・エラーの見え方がある |
| 言語とテーマ | 日本語と英語、明るいテーマと暗いテーマで崩れない。切り替えても作業の状態が変わらない |
| キーボード | 開く、値を直す、実行、カーソルで読む、比較、書き出し、保存までを、キーボードだけでできる |
| 見分けやすさ | 文字のコントラストは 4.5:1 以上、部品の輪郭と波形の線は 3:1 以上。波形の色は、色覚の型によらず全部の組が見分けられる（根拠は `design-system.md` 3章） |
| 作業を失わない | アプリ本体が動いている間は、ブラウザを再読み込みしても、仕様・編集内容・結果が元に戻る |
| オフライン | ネットワークが無くても、AI連携以外はすべて動く |
| データの扱い | 利用者のデータを外に送らない。AIに送る内容は送る前に画面で示す |

## 6. 技術

- 利用者のPCでローカルサーバー（FastAPI）を起動し、ブラウザで操作する。`circuit-sim` コマンドで起動し、ブラウザが開く。
- 画面は React + TypeScript（Vite）。ビルド結果をPythonパッケージに同梱する。
- 波形は uPlot を自前の Scope 部品で包む。間引きはサーバー側で行う。
- 書体、アイコン、スクリプトはすべて同梱する。外部から読み込まない。
- プロジェクト（仕様、結果、設定）は利用者が選んだフォルダにファイルで保存する。独自の隠し場所に溜めない。v0.1 は、仕様JSONとCSVをブラウザのダウンロードとして保存する（フォルダへの保存は v0.2 のプロジェクトの保存で設計する）。言語・テーマ・仕切りの位置のような画面の好みだけは、ブラウザに覚えさせる。

## 8. 起動コマンドの、OS ごとの動き

追記: ui-engineer（2026-11-16。A0 の Windows の実機での確認で分かったこと）。実装は `circuit_sim/app/cli.py`。

この章は、書いてあることの確かさを3つに分けて書く。

- **実機**: PO の PC（Windows 11 10.0.26200、Python 3.13.2）で確かめた事実。
- **資料**: Microsoft の文書、CPython・uvicorn のソースに書いてあること。実機では確かめていない。
- **未確認**: 直した後の Windows での動きなど、まだ確かめていないこと。Linux では、自動の試験で毎回確かめている。

### 8.1 止め方と終了コード

| 止め方 | 動き | 終了コード | Windows での確かさ |
|---|---|---|---|
| Ctrl+C | 保存していない変更があれば、1回目は知らせて止めない。10 秒以内の2回目で止める。「circuit-sim を止めました。」を出す | 0 | 未確認（別のプロセスから Ctrl+C を送れないので、手で確かめる）。Linux は、合図と疑似端末の両方で確かめている |
| Ctrl+Break（Windows） | Ctrl+C と同じ | 0 | 直す前は 3 で、「止めました」も出なかった（実機）。直した後は未確認 |
| 端末の窓を閉じる、ログオフ、シャットダウン（Windows） | Ctrl+Break と同じ合図として届く（資料）。OS がすぐにプロセスを終わらせるので、保存していない変更の知らせを人が読む時間は無く、後始末（転送用の HTML を消す）まで進むとは限らない。残った HTML は、次の起動で消す（期限より古いものだけ） | 決まらない | 未確認（手で確かめる） |
| SIGTERM（Linux、macOS） | 知らせずに止める。後始末をしてから、合図の既定の動きで終わる | -15 | 対象外 |
| 起動できなかった（ポートが使えない、設定の場所に書けない、引数の誤り） | 理由と直し方を出して終わる | 2 | ポートの使用中は実機で確かめた |

Ctrl+Break の終了コードが 3 になっていた理由:

- uvicorn は、止め終えた後に、受けた合図の扱いを元に戻してから、同じ合図を出し直す（資料: uvicorn 0.54.0 の `Server.capture_signals`）。
- SIGBREAK の元の扱いは「既定」。Windows で、既定の扱いの SIGBREAK を出すと、プロセスは終了コード 3 で終わる（**実機**: `python -c "import signal;signal.raise_signal(signal.SIGBREAK)"` の後の `%ERRORLEVEL%` は 3）。Microsoft の文書 `signal` は、既定では終了コード 3 で終わると書くが、その表に SIGBREAK は載っていない。根拠は実機の結果。
- `main` の終わりまで進まないので、「止めました」も出ない（実機の出力と合う）。
- 対策: 待ち受けている間、SIGBREAK の元の扱いを Ctrl+C の既定と同じ（`KeyboardInterrupt` を出す）にしておく（`cli.break_as_interrupt`。終わったら元に戻す）。出し直された合図は `main` に届き、Ctrl+C と同じ終わり方になる。
- 対策の確かさ: Windows の経路を、身代わりの合図（SIGUSR1）で Linux で流して確かめた（扱いがあれば終了コード 0 と「止めました」、無ければ合図の既定の動きで終わる）。Windows では未確認。

窓を閉じたときについて: Windows の C ランタイムは、Ctrl+C のほかのコンソールの合図（Ctrl+Break、窓を閉じる、ログオフ、シャットダウン）を、どれも SIGBREAK として渡す（資料: ucrt の `ctrlevent_capture`）。A0 では、ここに手を入れない。

残っている形（A1 へ持ち越す）: 止め終えた後、プロセスが終わるまでのわずかな間に2回目の合図が届くと、「止めました」は出るが、終了コードは 0 にならない。Ctrl+C でも同じで、前からある。

### 8.2 ポートを使えないときの見分け

`--port` で決めたポートで待ち受けられないとき、OS のエラーで案内を分ける。Windows では、Python が OS のエラー番号（winerror）から errno を作るので、両方を見る（`cli.port_problem`）。

| OS のエラー | Python の errno | winerror | 案内 |
|---|---|---|---|
| 使用中（POSIX の EADDRINUSE） | 98（Linux）、48（macOS） | 無い | 「ポート … は、ほかのプログラムが使っています」 |
| 使用中（Windows の WSAEADDRINUSE） | 10048 | 10048 | 同じ |
| 許されない（POSIX の EACCES。1024 未満のポートなど） | 13 | 無い | 「ポート … は使えません」と、`netstat`・`netsh` での確かめ方 |
| 許されない（Windows の WSAEACCES。OS が予約している範囲、ほかのプログラムの専用） | 13 | 10013 | 同じ |
| ほか | — | — | 「ポート … で待ち受けられませんでした」と OS の文 |

- 番号の出どころ（資料）: CPython の `PC/errmap.h`（`winerror_to_errno`。10013 は 10000 を引いて 13 にし、10048 はそのまま）と `Modules/errnomodule.c`（Windows の `errno.EADDRINUSE` は 10048）。Windows の実物の `OSError` がこの組になることは、Windows でだけ流れる試験が確かめる（未確認）。
- `netsh interface ipv4 show excludedportrange protocol=tcp` に出る範囲が、すべて「許されない」になるわけではない。`*` の印の範囲（管理者が足した除外）は、結べる。
- **実機**: PO の PC の netsh の出力は `50000 50059 *` の1行。最初の全体の確認のとき、試験がこの範囲の先頭（50000）を `--port` に渡して起動し、起動は成功した（`*` の範囲のポートを結べた）。試験は止めずに終わり、アプリ本体が 50000 で待ち受けたまま残った。流し直しで「ポート 50000 は、ほかのプログラムが使っています」と出たのは、その残りがポートを持っていたためで、製品の案内は実態と合っていた。残りは PO が止めた。
- ほかの PC でも、`50000 50059 *` が出力に見られる（公開されている質問の中の出力例。下の出どころ）。どの Windows にも既定であるとは、確かめていない。

### 8.3 ブラウザの開き方と、端末の Enter

- ブラウザは、Python の `webbrowser.open` に、転送用の HTML の場所（`file:///…`）を渡して開く。Windows の既定は `os.startfile`（資料: `Lib/webbrowser.py`）。
- 環境変数 BROWSER の指定は、OS の既定の候補の「前」に足されるだけで、既定の候補は残る。BROWSER のコマンドが失敗すると（起動できない、0 でない終了コード）、`webbrowser` は OS の既定のブラウザへ進む（資料: 同じファイルの `register_standard_browsers` と `open`。Linux では、試験で確かめている）。
- BROWSER のコマンドは、Python が名前を知らないものなら、終わるまで `webbrowser.open` が戻らない。終わりに `&` を付けた指定は、起動してすぐ戻る（資料: 同じファイルの `GenericBrowser` と `BackgroundBrowser`）。どちらも、標準入力を差し替えずに起動する。起動される側は、アプリ本体と同じ標準入力を持つ。
- **実機**: 標準入力がパイプで、スレッドがそのパイプを読んで待っている（`os.read(0, 1)`）間に、標準入力を差し替えずに起動した子（`python -c pass`）は、5 秒たっても終わらない。読んで待たない対照は、すぐ終わる。
  - 仕組み（資料）: Windows の同期のハンドルは、操作を1つずつしか通さない。Python は、起動のときに標準入力の位置を調べるので、読み取りの待ちが終わるまで、そこで止まる（CPython の issue 78961）。
  - 最初の全体の確認で、標準入力がパイプの起動のときに BROWSER の偽のブラウザが 30 秒たっても呼ばれず、案内も出なかったのは、これ（`webbrowser.open` が、始まれない子の終わりを待ち続けた）。本物のブラウザは開いていない（実機: PO の観察）。
- 対策: **Windows で標準入力がパイプのときは、待たない読み方をする**（`cli.watch_enter`）。
  - `PeekNamedPipe` で、届いている量を、読まずに調べる（`cli.windows_pipe_ready`）。届いていれば、届いた分だけ読む。届いていなければ 0.05 秒眠って、調べ直す。
  - 調べる呼び出しが待つか（資料）: Microsoft の文書 PeekNamedPipe が書くのは、「1つのスレッドのアプリケーションでは、いつもすぐ戻る」と、注記「複数のスレッドのアプリケーションで同期のハンドルに使うと、ほかの入出力と同じように待つことがある」まで。アプリ本体は複数のスレッドなので、文書からは「すぐ戻る」とは言えない。
  - 推定（未確認）: 同期のハンドルの操作は1つずつになる（Raymond Chen の記事）ので、標準入力を受け継いだ別のプロセスも含めて、同じパイプをほかに読むものがいなければ、調べる呼び出しはすぐ戻る。そうなら、パイプに読み取りの待ちを残さず、起動される側は止まらない。「待たない」と言えるのはここまで（下の「残る制限」）。
  - 眠る時間 0.05 秒は、Enter を押してから新しい URL が出るまでの遅れの上限（原則 5 の 0.1 秒に収まる）。調べるのは 1 秒に 20 回で、届かない間も CPU をほとんど使わない（Linux で、身代わりの調べ方を使って確かめている。Windows の本物の `PeekNamedPipe` では未確認）。
  - 書く側が閉じたら（`PeekNamedPipe` の失敗が ERROR_BROKEN_PIPE 109 か ERROR_PIPE_NOT_CONNECTED 233）、読むのをやめる。止めるときは、眠りからすぐ抜ける。
  - パイプとして調べられない入力（ほかの失敗）と、調べる用意ができないとき（`ctypes` や `msvcrt` が使えない、など）は、待つ読み方に戻す（Enter は読めるが、上の止まり方は残る。ソケットを標準入力にした起動などで、ふつうは通らない）。
  - 端末（コンソール）の読み方と、Windows でない OS の読み方は、変えていない（待つ読み方）。ファイルや NUL が標準入力のときは、前と同じく読まない。
  - 確かさ: 待たない読み方の道は、Linux で、本物のパイプと身代わりの調べ方で流して確かめている。`PeekNamedPipe` の呼び方と答えの読み方は、API を差し替えて確かめている（値は Microsoft の文書）。**Windows の本物では未確認**（Windows でだけ意味を持つ試験を足した: 製品の読み方で待っている間に、子が始まれること）。
- 残る制限（待たない読み方でも、なくならないもの）:
  - **標準入力を受け継いだ側が、標準入力を読むとき。** BROWSER のコマンドなど、標準入力を受け継いだプログラムが標準入力を読むと、Enter はそちらが取る。そのプログラムが読んで待っている間は、`PeekNamedPipe` も待たされ、その間 Enter は効かない見込み（推定。根拠は上の文書の注記と、Raymond Chen の記事の説明。実機でも、自動の試験でも確かめていない）。だから、「待たずに調べる」とは言い切らない。言えるのは「受け継いだ別のプロセスも含めて、同じパイプをほかに読むものがいない限り、待たない（推定）」まで。`windows_pipe_ready` が作った関数は、Enter を読むスレッドの中だけで呼ぶ（`windows_pipe_ready` そのものは、`watch_enter` を呼んだスレッドで呼ばれ、関数を作るだけ）。
  - **調べてから読むまでの間に、別の読み手が先に取ったとき。** `os.read` は、次に届くまで待つ（その間は、上の止まり方が起こりうる）。別の読み手がいなければ起こらない。
  - **端末（コンソール）は、待つ読み方のまま。** コンソールで起動して BROWSER にコマンドを指定したとき、そのコマンドが始まれるかは、未確認（実機の診断は、パイプだけを確かめた）。BROWSER を指定しない起動（ふつうの使い方。`os.startfile`）は、標準入力を受け継ぐ子をアプリ本体が起動しないので、この止まり方には当たらない見込み（未確認）。手で確かめる項目は 8.5。
  - **0.05 秒の間に届いた複数の Enter は、1回になる。** 眠りの間に届いた分は1回の読み取りに入り、1回の読み取りに改行があれば1回と数える（数え方は待つ読み方と同じ。CR と LF が別々の読み取りに分かれて届くと2回になるのも同じ）。
  - **端末がパイプに見える環境。** Git Bash（mintty）などから起動すると、Windows のプログラムから見た標準入力はパイプになる見込みで、人が打つ Enter も待たない読み方を通る（未確認。8.5）。
- Enter は、起動の直後から読む。ブラウザを開く呼び出しが戻るのを待たない（BROWSER のコマンドが終わるまで戻らない形でも、ブラウザを開いたまま Enter が効く。そのコマンドが標準入力を読まない限り）。
  - 一度、「ブラウザを開く呼び出しが戻ってから読み始める」やり方にしたが、ブラウザを閉じるまで Enter が効かなくなる後退だったので、やめた（レビュー 5回目の中1）。
- 決まり: アプリ本体から別のプログラムを起動するときは、標準入力を必ず差し替える（`subprocess` の `stdin=DEVNULL` など）。待たない読み方にしても、端末でない入力をほかの読み方で読む部分を足せば、同じ止まり方が起こりうる。

### 8.4 試験の決まり（Windows で落ちた理由から）

- **起動したプロセスは、必ず止める。** アプリの試験（`tests/test_app_*.py`）は、`tests/app_procs.py` を通して起動する。起動したものは控えに入り、試験の終わりに動いていたら、見張りが止めて、その試験を失敗にする。「起動に失敗して終わるはず」の起動は、終わらなければ止めてから落とす（`run_to_end`）。きっかけは 8.2 の実機の事実（試験が、PO の PC にアプリ本体を残した）。
  - 子も止めるのは、親が動いている間にたどれる子だけ。POSIX は、親を一時停止してから子と孫をたどり、一時停止したものに、子から先に SIGKILL を送る。止まっている親の子の番号は、親が SIGCHLD を無視していない・一時停止が効いた後・ほかの者が親を止めない、の条件のもとで使い回されない（試験が起動するものは、どれも SIGCHLD を無視しない）。たどる途中で例外（後始末の最中の Ctrl+C など）が起きても、一時停止したものは必ず止める（止まったまま残さない。レビュー 7回目の中1）。Windows は `taskkill /T`。親が先に終わった子は、止めも知らせもしない（POSIX では、試験と同じまとまりにいれば、ハーネスが時間切れや中断で確認をまとまりごと止めたときには止まる。確認がふつうに終わったときは止まらない）。
  - 起動したものは、試験のプロセス（pytest）と同じプロセスのまとまりに置く（POSIX）。ハーネス（`scripts/local_ci.py`）が時間切れや中断で確認をまとまりごと止めても、一緒に止まる。新しいまとまりが要る起動（疑似端末を、そのプロセスの端末にする試験）は `spawn(new_session=True)` にし、試験のプロセスが終わったら止める見張り（命綱のパイプ。`select.poll` で見るので、fd の番号によらない）を付ける（検証 6回目の問題2）。
  - 確かめ終えた（終わっている）ものは控えから外し、持っていたパイプを閉じる（控えが、試験の数に比例してパイプを持ち続けない）。
  - 既知の限界: pytest のプロセスだけが強制終了されると（メモリ不足など。まとまりごとでない止め方）、見張りは働かず、ふつうの起動は残る（新しいまとまりの起動は、命綱の見張りが止める）。`taskkill /T` は親の番号で子をたどる。Windows の子の「親の番号」は、子が作られたときの写しで、親が終わった後に別のプロセスに使い回されうる（資料: Raymond Chen の記事）ので、無関係のプロセスを子と見て止める可能性がある（`taskkill` が作られた時刻で見分けているかは、文書に無い。未確認。`scripts/cycle.py` も同じ）。
- **端末の出力は、待つ上限つきで読む。** 製品が何も出さなくなる後退が入ったとき、試験が止まらずに落ちるように。
- ブラウザを開く起動（`--no-browser` を付けない起動）の試験は、偽のブラウザが失敗しても OS の既定のブラウザへ進まない見張りを付けて起動する（`tests/test_app_cli.py` の `BROWSER_GUARD`）。終わるはずの起動（`--help`、引数の誤り）にも `--no-browser` を付ける。
- `parametrize` の値が長い・日本語のときは、短い `ids` を付ける。pytest は実行中の試験の ID を環境変数に入れ、Windows の環境変数は 32767 文字までなので、長い ID の試験は準備の段階でエラーになる（実機）。アプリの試験は 200 文字までと決め、試験で確かめる。
- パスを決め打ちにしない。絶対パスの決まりは OS と Python の版で違う（`/x/conf` は、Windows の Python 3.13 から絶対パスではない。手元の 3.11・3.12・3.13 の `ntpath.isabs` で確かめた）。
- Windows だけの分岐を、OS の呼び出しを差し替えて Linux で流すときは、差し替える値を、実機の値か資料の値に合わせ、どちらなのかと出どころを書く。
